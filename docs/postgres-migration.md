# ย้ายจาก sqlite แบบ sync ไป Postgres

บันทึกนี้เขียนหลังจากลองทำแล้วไม่สำเร็จหนึ่งครั้ง เพื่อไม่ให้ครั้งหน้าเริ่มจากศูนย์
และไม่ให้ใครลองวิธีเดิมซ้ำ

## ทำไมต้องย้าย

`node:sqlite` เป็น API แบบ sync และไฟล์อยู่ที่ `/tmp` บน Vercel ซึ่งเป็นของ
instance ใครของมันและหายเมื่อคอนเทนเนอร์เย็น วัดได้จริงบน production:
คำขอแรกไปที่ `/app` ใช้ **11.17 วินาที** เพราะสร้างฐานข้อมูลใหม่ทั้งชุด
คำขอถัดมา 0.44s

แปลว่าอะไรที่ผู้ใช้กรอกหรืออนุมัติจะหายไป ระบบนี้จึงยังรับข้อมูลลูกค้าจริง
ไม่ได้ — ไม่ใช่เพราะฟีเจอร์ไม่พอ

Postgres คุยผ่านเครือข่าย จึงเป็น async โดยธรรมชาติ การเรียกแบบ sync ทั้งกอง
คือสิ่งเดียวที่กั้นอยู่

## สิ่งที่พร้อมแล้ว

- `lib/engine/sql.ts` — adapter async ที่รองรับสองตัวขับ เลือกจาก `DATABASE_URL`
  มีคือ Postgres ไม่มีคือไฟล์ sqlite รวมถึง `toDollarPlaceholders()` (`?` → `$n`)
  และ `tx()` แบบ callback ที่บังคับให้ทุกคำสั่งอยู่บนคอนเนกชันเดียวกัน
- ตัวช่วยระดับโมดูล `all` `get` `run` `exec` `tx` — หน้าตาที่จุดเรียกจะย้ายมาใช้
- `supabase/migrations/0001_schema.sql` และ `0002_rls.sql`

ทั้งหมดนี้**ยังไม่มีใครเรียก** เป็นโครงที่รออยู่

## วิธีที่ลองแล้วไม่ได้ผล

เขียนสคริปต์แปลงรูปแบบ `db().prepare(Q).all(args) as T[]` เป็น
`await all<T>(Q, ...args)` แบบกวาดทั้งโปรเจกต์

ล้มสองครั้ง เพราะโค้ดมีรูปแบบการเรียกอย่างน้อยห้าแบบ:

1. เรียกทันที — `db().prepare(Q).all(a)`
2. เก็บคอนเนกชันไว้ก่อน — `const d = db();` แล้ว `d.prepare(...)`
3. เก็บ statement ไว้ใช้ซ้ำในลูป — `const ins = db().prepare(Q)` แล้ว `ins.run(...)`
4. ห่อวงเล็บทั้งก้อน — `const x = (db().prepare(Q).get(a) as T)`
5. `db().prepare(` ที่อยู่ในคอมเมนต์ ซึ่งไม่ควรถูกแตะ

แบบ 4 กับ 5 ทำให้ตัวแปลงเขียนไฟล์ที่ไวยากรณ์พัง และการไล่ซ่อมทีหลังแพงกว่า
การย้อนทั้งหมด — ซึ่งเป็นสิ่งที่ทำไปในที่สุด

และการ cast ชนิดข้อมูลอย่าง `as { kind: string; n: number }[]` มี `;` อยู่ข้างใน
regex ที่หยุดที่ `;` จึงตัดกลางชนิดข้อมูล ได้ `all<{ kind: string>(...)` ออกมา

## วิธีที่ควรใช้ครั้งหน้า

ทีละไฟล์ ไม่ใช่กวาดทั้งโปรเจกต์ และหลังทุกไฟล์ต้องผ่านสี่ด่านก่อนไปไฟล์ถัดไป:

```
npm run typecheck && npm run check && npm run verify && npm run verify:tenants
```

ลำดับจากใบไปราก เพราะแต่ละไฟล์ที่เสร็จจะทำให้ typechecker ชี้ผู้เรียกถัดไปเอง:

```
db.ts → derive.ts → seed.ts → match.ts → proof.ts → billing.ts
      → dispatch.ts → ingest.ts → demo.ts → ai.ts → bootstrap.ts
      → app/(app)/**
```

`db.ts` เปลี่ยนบทบาทจากตัวถือคอนเนกชันเป็นตัวดูแลสคีมาฝั่ง sqlite อย่างเดียว
(`ensureSchema()`), `db()` หายไป และ **typechecker คือเครื่องมือที่ทำให้งานนี้
ปลอดภัย** — มันจะไล่รายชื่อผู้เรียกที่ต้องเติม `await` ให้ครบเอง

รูปแบบที่ 3 (statement ใช้ซ้ำ) กลายเป็นค่าคงที่ของข้อความ query แล้วเรียก
`await run(Q, ...)` ในลูป ฝั่ง Postgres ไม่เสียอะไรเพราะตั้ง `prepare: false`
อยู่แล้ว (Supavisor โหมด transaction ไม่รองรับ statement ที่ผูกกับคอนเนกชัน)
ส่วนฝั่ง sqlite เสียการ cache statement ไปบ้าง แต่ทุกก้อนนี้อยู่ใน `tx()`
ซึ่งเป็นตัวกำหนดความเร็วจริงของการนำเข้า

## สองสคีมาต้องเดินคู่กัน

`lib/engine/db.ts` ถือ DDL ฝั่ง sqlite · `supabase/migrations/0001_schema.sql`
ถือฝั่ง Postgres สองไฟล์เพราะสองภาษาถิ่นของ SQL ไม่ใช่เพราะสองความจริง
แก้ที่หนึ่งต้องแก้อีกที่ทันที ชุดตรวจจะจับได้ก็ต่อเมื่อรันบนตัวขับที่แก้ไปแล้ว

## ที่ยังขาดก่อนเริ่มได้จริง

ยังไม่มีโปรเจกต์ Supabase และไม่มี environment variable บน Vercel เลยสักตัว
(`vercel env ls` คืนค่าว่าง) แปลว่าต่อให้แปลงโค้ดเสร็จสมบูรณ์ **ก็ยังทดสอบ
ฝั่ง Postgres ไม่ได้เลย** — ทดสอบได้แค่ว่าโค้ดที่แปลงแล้วยังทำงานถูกบน sqlite

ต้องมีก่อน:

1. โปรเจกต์ Supabase
2. `DATABASE_URL` ที่ชี้ไป Supavisor **โหมด transaction** (พอร์ต 6543)
3. รัน `supabase/migrations/0001_schema.sql` และ `0002_rls.sql` บนโปรเจกต์นั้น

⚠ connection string ต้องเป็นของผู้ใช้ที่ล็อกอิน **ไม่ใช่ service role** —
ถ้าใช้ service key ตรงนี้ RLS จะถูกข้ามทั้งหมดและ `0002_rls.sql` จะไม่ได้กัน
อะไรเลย

## Auth ต้องมาก่อนหรือหลัง

RLS ปกป้องตามคำถามว่า "ผู้ใช้คนนี้เป็นใคร" ซึ่งตอนนี้ยังไม่มีคำตอบ — บัญชีที่
เปิดอยู่คือค่าในคุกกี้ `parallax_tenant` และ `switchTenantAction` เขียนกำกับไว้
เองว่าเป็นของเดโม ไม่ใช่การควบคุมสิทธิ์

ย้าย Postgres ได้ก่อนโดยไม่มี auth (ข้อมูลจะคงอยู่ แต่ยังไม่มีการแบ่งสิทธิ์)
แต่**ห้ามรับข้อมูลลูกค้าจริงจนกว่าจะมีทั้งสองอย่าง**
