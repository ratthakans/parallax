## 1 · ทิศในประโยคเดียว

> เจ้าของ 2026-10-13: *"อยากให้มีความเป็น multidimension crm"* — ยืนยันนิยามและเกณฑ์ด้านล่างแล้ว

**PARALLAX คือ Multidimensional CRM — CRM ทั่วไปเห็นลูกค้าเป็นรายชื่อ PARALLAX เห็นทุกมิติของความสัมพันธ์**

### นิยาม (เราเป็นคนกำหนด)

คำว่า "multidimensional CRM" ยังไม่มีความหมายกลางในตลาด — เจ้าอื่นใช้ในความหมาย "หลายธุรกิจในระบบเดียว"
หรือ "วิเคราะห์ข้อมูลหลายมุม" เราจึงต้องนิยามเองให้ชัดและพิสูจน์ได้ในเดโม

| | CRM ทั่วไป · มิติเดียว | PARALLAX · หลายมิติ |
|---|---|---|
| หน่วยข้อมูล | คนหนึ่งคน = แถวเดียว | คนหนึ่งคน = จุดตัดของหลายแกน |
| สถานะ | สถานะเดียว (ลีด → ลูกค้า) | บทบาทต่อโปรแกรมต่อช่วงเวลา (ผู้เข้าชม 2017 · ผู้ออกบูธ 2020 · วิทยากร 2024) |
| องค์กร | ช่องข้อความ "บริษัท" | สังกัดที่มีช่วงเวลา — รู้ว่าย้ายงานเมื่อไร ไปไหน |
| คุณภาพข้อมูล | ไม่มี — สมมุติว่าสะอาด | ห้ามิติต่อคน (หัวข้อ 5) |
| การแบ่งกลุ่ม | ตัวกรองทีละช่อง | ไขว้แกนใดก็ได้ ทุกช่องที่ไขว้คือกลุ่มที่ใช้งานได้ทันที |
| ความเหมาะสม | คะแนนลีดก้อนเดียว | คะแนนต่องาน — คนเดียวเหมาะกับงานหนึ่ง ไม่เหมาะกับอีกงาน |

- **แกนโครงสร้าง:** คน × องค์กร × โปรแกรม × บทบาท × เวลา (หัวข้อ 4)
- **แกนคุณภาพ:** ติดต่อได้ไหม · เป็นใคร · เคยทำอะไรกับเรา · อนุญาตอะไรไว้ · เหมาะกับงานไหน (หัวข้อ 5)

ชื่อยังใช้ได้พอดี — parallax คือการมองสิ่งเดียวจากหลายจุดจนเห็นความลึก

### กว้างที่ตำแหน่ง แคบที่จุดเจาะ

| | |
|---|---|
| **ตำแหน่งในตลาด** | Multidimensional CRM สำหรับองค์กร B2B |
| **กลุ่มที่เจาะก่อน** | องค์กรที่มีโปรแกรมซ้ำทุกปี — งานแสดงสินค้า/สัมมนา · สมาคม/สมาชิก · หลักสูตรอบรม เพราะทุกมิติมีข้อมูลเต็ม จึงเห็นความต่างจาก CRM ทั่วไปชัดที่สุด |
| **ที่มา** | ปัญหาที่เห็นจาก SETA (หัวข้อ 2) — **ไม่ได้สร้างเพื่อ SETA รายเดียว** ทุกอย่างที่เฉพาะกลุ่มลูกค้าเป็นข้อมูล (แม่แบบงาน · คำเรียก) ไม่ใช่โค้ด |
| **ระดับตลาด** | **Premium ไม่ใช่ mass market** — ลูกค้าน้อยราย มูลค่าต่อรายสูง ขายผ่านการคุย ดูแลใกล้ชิด (หัวข้อ 1.1) |
| **"Corporate"** | หมายถึงข้อมูลแบบ B2B (คนในฐานมาจากองค์กร) ไม่ได้แปลว่าขายให้องค์กรมหาชนก่อน — ลูกค้ารายแรกเป็นองค์กรขนาดกลาง |

ประโยคขายรอง: **"ฐานข้อมูล 10 ปีของคุณ ใช้ได้จริงกี่คน — และควรใช้ทำอะไร"**

### 1.1 · Premium ไม่ใช่ mass market

เป็นการเลือกเชิงกลยุทธ์ ไม่ใช่แค่ราคาแพง — มันเปลี่ยนวิธีสร้าง วิธีขาย และสิ่งที่ไม่ทำ

| เรื่อง | Mass market (ไม่ทำ) | PARALLAX (premium) |
|---|---|---|
| ลูกค้า | ใครก็สมัครได้ หลักพันราย | **องค์กรที่ผ่านเกณฑ์** หลักสิบรายต่อปี |
| การขาย | สมัครเอง · แผนฟรี · บัตรเครดิต | **นัดคุย → ตรวจฐานข้อมูล (Database Audit) → สัญญารายปี** |
| เริ่มใช้ | ลูกค้าย้ายข้อมูลเอง | **เราย้ายและล้างข้อมูลให้** (white-glove) · ได้ผลสแกนในสัปดาห์แรก |
| สิ่งที่ขาย | ฟีเจอร์ | **ผลลัพธ์**: ฐานข้อมูลที่ใช้ได้ + งานที่เปลี่ยนเป็นรายได้ + ผลที่วัดได้ |
| ผลิตภัณฑ์ | ทำได้หลายอย่างพอใช้ | ทำไม่กี่อย่าง **แต่ลึกและแม่น** — การรวมคนซ้ำ มิติ งาน ต้องดีกว่าทุกเจ้า |
| ความรู้สึก | เครื่องมือ | **ห้องควบคุมข้อมูลขององค์กร** — ดีไซน์ ความเร็ว ภาษา ต้องระดับผู้บริหารเปิดในห้องประชุมได้ |
| การดูแล | ศูนย์ช่วยเหลือ | ผู้ดูแลลูกค้าที่รู้จักข้อมูลของเขา · ทบทวนสุขภาพฐานข้อมูลรายไตรมาส |

**เกณฑ์ลูกค้าที่รับ (ICP)** — ต้องผ่านอย่างน้อย 3 ใน 4:
1. มีคนในฐานข้อมูลสะสม ≥ 20,000 คน หรือข้อมูลย้อนหลัง ≥ 3 ปี
2. ความสัมพันธ์หนึ่งรายมีมูลค่าสูง (บูธ · สปอนเซอร์ · ค่าสมาชิกองค์กร · หลักสูตร · ดีล B2B)
3. ข้อมูลกระจายหลายทีม/หลายแบรนด์/หลายระบบ
4. มีคนรับผิดชอบรายได้ที่ต้องตอบผู้บริหารว่าฐานข้อมูลสร้างรายได้เท่าไร

ไม่ผ่านเกณฑ์ = ไม่ใช่ลูกค้าของเรา แม้อยากจ่าย — ลูกค้าที่ไม่เหมาะกินแรงทีมเล็กและดึงผลิตภัณฑ์ไปทางอื่น

### 1.2 · คอนเซ็ปต์: Depth Database

**PARALLAX — The Depth Database for relationship-driven organisations**
ไทย: **"ฐานข้อมูลความสัมพันธ์ ที่มองเห็นทุกมิติ"**

> Salesforce บอกว่าคุณมีลูกค้ากี่คน — PARALLAX บอกว่าใครเป็นคนจริง ยังใช้ได้ไหม มาจากไหน และควรใช้ทำอะไร

ชื่อ parallax มาจากทัศนศาสตร์ (มองจากหลายจุดจึงเห็นความลึก) → ทั้งผลิตภัณฑ์ใช้ภาษาเดียวกันนี้
ชื่อโมดูลเป็นภาษาอังกฤษ (แบรนด์ จำง่าย ใช้ในห้องประชุมได้ทั้งไทยและต่างชาติ) คำอธิบายบนหน้าจอเป็นไทย:

| โมดูล | คืออะไร | ความหมายในภาษาแสง |
|---|---|---|
| **Sources** | ทุกไฟล์ ทุกระบบที่ส่งข้อมูลเข้า พร้อมแม่แบบจับคู่และลำดับความน่าเชื่อถือ | แหล่งแสง |
| **Golden Record** | เรคคอร์ดจริงหนึ่งเดียวของแต่ละคน/องค์กร (คำมาตรฐานของงาน MDM ที่ผู้ซื้อระดับ pro รู้จัก) | ภาพที่โฟกัสแล้ว |
| **Depth** | ห้ามิติ + ไทม์ไลน์บทบาท บนทุกเรคคอร์ด | ความลึก |
| **Clarity** | คะแนนความคมชัดของฐานข้อมูล 0–100 ตามเวลา ตามแหล่ง ตามทีม | ความคมชัด |
| **Prism** | ตารางไขว้หลายมิติ — แยกฐานข้อมูลก้อนเดียวออกเป็นทุกมิติ | ปริซึมแยกแสง |
| **Lens** | มุมมองที่บันทึกไว้ (กลุ่มที่นับใหม่เอง) มีเจ้าของและวัตถุประสงค์ | เลนส์ |
| **Focus** | งาน: เป้าหมาย + กฎคัด + คะแนน + ปลายทาง (หัวข้อ 6) | จุดโฟกัส |
| **Calibrate** | ห้องทำงานของผู้ดูแลข้อมูล: คู่ที่ไม่แน่ใจ · ป้ายที่ระบบเดา · ค่าที่ผิดกฎ | การปรับเทียบ |
| **Trace** | ที่มาของทุกค่า + ประวัติการแก้ + ย้อนดูเรคคอร์ด ณ วันใดก็ได้ | เส้นทางแสง |
| **Rule Lab** | ทดลองกฎ (รวมคน · เลือกค่า · ตรวจ · มิติ) บนสำเนา เห็นผลต่างก่อนใช้จริง | ห้องทดลอง |
| **Consent Ledger** | สมุดบัญชีความยินยอมต่อวัตถุประสงค์ พร้อมหลักฐาน แก้ย้อนหลังไม่ได้ | — |
| **Signals** | ผลที่ไหลกลับ (เด้ง · เปิด · ลงทะเบียน · ดีลได้) แล้วปรับ Depth | สัญญาณ |
| **Triggers** | อัตโนมัติเมื่อมิติเปลี่ยน ("องค์กรกลายเป็นผู้ออกบูธที่หายไป → สร้างงานให้เจ้าของ") | — |
| **Steward** | ผู้ช่วย AI ดูแลข้อมูล ใช้ **Claude ของ Anthropic** — 18 ความสามารถ เสนอเท่านั้น คนอนุมัติเสมอ (`ai-plan.md`) | — |

**ตัวเลขผู้บริหาร: Relationship Equity** — มูลค่าโดยประมาณของฐานข้อมูล
(มูลค่าที่เคยเกิดของแต่ละองค์กร × โอกาสติดต่อได้ × ได้รับอนุญาต) แสดงเป็นเส้นตามเวลา
ทำให้ "ล้างฐานข้อมูล" กลายเป็นตัวเลขที่ผู้บริหารเห็นว่าโตขึ้น — **ป้าย "ประมาณการ" และเปิดวิธีคิดให้ดูเสมอ** (P9)

### 1.3 · ระดับ pro เทียบ Salesforce

**คำตอบตรง:** ทั้งแพลตฟอร์ม — ไม่ และไม่ควร (Salesforce มีแอปหลายพัน ภาษาโปรแกรมของตัวเอง งานบริการ CPQ)
**ในชั้นจัดการฐานข้อมูลความสัมพันธ์ — ได้ และบางข้อเกิน** ซึ่งคือสิ่งที่ผู้ซื้อ premium ตรวจจริง

| Salesforce | PARALLAX | |
|---|---|---|
| Object Manager · ฟิลด์กำหนดเอง · picklist · formula | **Schema**: ฟิลด์กำหนดเอง · ชุดคำแบบลำดับชั้น · ฟิลด์คำนวณ · ชนิดเรคคอร์ดต่อกลุ่มลูกค้า | 🟰 |
| Validation Rules | กฎตรวจค่า (บังคับกรอก · รูปแบบ · ตามขั้นของดีล) → ค่าที่ผิดเข้า Calibrate | 🟰 |
| Duplicate & Matching Rules + **Data 360 identity resolution** (match rules + reconciliation rules → unified profile) — ผลิตภัณฑ์แยกจาก Sales Cloud | **Golden Record** ในตัว: ชุดกฎจับคู่ (ตรงตัว · ปรับรูป · คล้าย) + กฎเลือกค่าต่อฟิลด์ + ลิงก์กลับแหล่งทุกค่า + ยกเลิกการรวมได้ | ✅ อยู่ในตัว ไม่ต้องซื้อเพิ่ม · เข้าใจชื่อและองค์กรไทย |
| Field History Tracking (จำกัดจำนวนฟิลด์ เว้นแต่ซื้อเพิ่ม) | **Trace**: ทุกฟิลด์ · ย้อนดู ณ วันใดก็ได้ · กู้ค่าเดิม | ✅ |
| Sandbox | **Rule Lab**: ทดลองกฎข้อมูลบนสำเนาแล้วเห็นผลต่าง (ไม่ใช่สำเนาทั้งระบบ) | 🟰 สำหรับงานข้อมูล |
| List Views | **Lens** | 🟰 |
| Reports & Dashboards | **Prism** + แดชบอร์ด | 🟰 · ตารางไขว้ข้ามมิติคุณภาพได้ |
| Data Import Wizard · Data Loader | **Sources** + bulk API | ✅ อ่านไฟล์ไทยยุ่ง ๆ ได้ |
| Profiles · Roles · Sharing Rules · Field-Level Security | **Governance**: บทบาท · ขอบเขตการเห็น · ซ่อนฟิลด์ · โอนพอร์ต | 🟰 |
| Setup Audit Trail · Event Monitoring (Shield) | บันทึกการตั้งค่า + การเข้าถึง + การเปิดค่าจริง · PII เข้ารหัสเป็นค่าตั้งต้น | 🟰 |
| Flow | **Triggers** (เมื่อ … ถ้า … ให้ …) — จำกัดกว่า | ⚠️ ตั้งใจ |
| Einstein / Agentforce | **Steward** (Claude) — เน้นงานดูแลข้อมูล: อ่านไฟล์ · จัดหมวด · ตรวจคู่ซ้ำ · ถามภาษาไทยแล้วได้ Prism · สรุปที่ชี้ที่มาทุกประโยค | 🟰 คนละจุดเน้น · รวมในสัญญา ไม่ต้องซื้อเพิ่ม |
| Campaigns · ROI | **Focus** + อีเมล + **กลุ่มควบคุมจริง** | ✅ วัดผลที่เกิดเพราะเราจริง |
| Opportunities | ท่อขาย | 🟰 พื้นฐาน |
| Consent (Privacy Center — ซื้อเพิ่ม) | **Consent Ledger** ต่อวัตถุประสงค์ ตาม PDPA | ✅ |
| AppExchange · Apex · Service Cloud · CPQ · Territory | ไม่ทำ | ❌ ตั้งใจ |

แหล่งอ้างอิงแนวคิด identity resolution ของ Salesforce: Trailhead *Unify Your Data* และ *Identity Resolution Ruleset*

### เกณฑ์ 30 วินาที — ถ้าเดโมไม่แสดงสี่ข้อนี้ "multidimensional" เป็นแค่คำโฆษณา

1. **คนเดียว หลายบทบาท หลายปี** — เปิด Golden Record ของคนหนึ่งคน เห็นไทม์ไลน์บทบาทข้ามโปรแกรมและปี พร้อมการย้ายองค์กร
2. **Prism** — เลือกสองแกนใดก็ได้ (เช่น อุตสาหกรรม × ระดับ) กรองด้วยแกนที่สาม (ติดต่อได้) กดช่องไหนได้รายชื่อทันที
3. **คะแนนต่างกันตาม Focus** — คนเดียวกันได้คะแนนสูงในงานหนึ่ง ต่ำในอีกงาน พร้อมเหตุผลทั้งสองฝั่ง
4. **Trace** — กดค่าใดก็ได้บนเรคคอร์ด เห็นว่ามาจากไฟล์ไหน แถวไหน กฎไหนเลือกค่านี้ และค่าเดิมคืออะไร

ทั้งสี่ข้อเป็น **เกณฑ์ผ่านอัตโนมัติ** ใน `verify:demo` (ดู `dev-plan.md`) ไม่ใช่แค่สิ่งที่หวังว่าจะมี

## 2 · ที่มา: ปัญหาที่เห็นจาก SETA

PARALLAX เดิมเป็น CRM ที่ sync กับ POS สำหรับร้านค้าปลีก การได้เห็นปัญหาการจัดการฐานข้อมูลของ SETA
(ซึ่งเป็นลูกค้าของเราในมุมอื่น) ทำให้เปลี่ยนทิศมาเป็น B2B CRM ที่เน้นมิติหลากหลาย

**SETA คือกรณีที่ทำให้เห็นปัญหาชัด ไม่ใช่ขอบเขตของผลิตภัณฑ์** — ปัญหาเดียวกันมีในทุกองค์กรที่สะสมความสัมพันธ์มาหลายปี
(หัวข้อ 12) จะเป็นลูกค้านำร่องหรือไม่ เป็นเรื่องที่คุยกันแยก (P2)

### รูปทรงของข้อมูล (จากหน้าเว็บสาธารณะ setaasia.com ณ 2026-10-13)

| | |
|---|---|
| ผู้จัด | GAT International Co., Ltd. กรุงเทพฯ |
| แบรนด์ที่สะสมมา | SETA · Solar+Battery Expo · SustainAsia Week · SETA Summit 2025 · **Powerverse Thailand 26 พ.ย. 2026** (BITEC) |
| หมวด | พลังงานสะอาด · ประสิทธิภาพพลังงาน · โซลาร์และแบตเตอรี่ · EV · การเงินสีเขียว · นโยบาย |
| ตัวเลขที่ประกาศ (2024) | ผู้ร่วมงาน 10,000+ · VIP 500+ · ผู้ออกบูธ 100+ · วิทยากร 300+ · 45+ ประเทศ |
| บทบาทของคนในฐาน | ผู้เข้าชม · ผู้ออกบูธ · วิทยากร · VIP (ผู้บริหาร · ผู้กำหนดนโยบาย · นักลงทุน) · สปอนเซอร์ · พันธมิตรสื่อ · ผู้ติดต่อผ่านฟอร์ม · ผู้ติดตามโซเชียล |

### ปัญหาที่เจ้าของเล่า แปลเป็นข้อมูล

| ที่เจ้าของพูด | ข้อมูลที่หายไป |
|---|---|
| "ไม่รู้อันไหนใช้ได้" | ไม่มีสถานะการติดต่อได้ต่อคน (มิติ 1) |
| "จัดการยังไง" | คนเดียวอยู่หลายไฟล์ หลายแบรนด์ หลายปี ไม่มีเรคคอร์ดกลาง (หัวข้อ 8) |
| "grouping ยังไง" | ไม่มีตำแหน่ง/อุตสาหกรรมที่เป็นมาตรฐาน ไม่มีประวัติการมีส่วนร่วม (มิติ 2–3) |
| "สอดคล้องกับงานไหน" | ไม่มีตัวเชื่อมระหว่างกลุ่มคนกับเป้ารายได้ (หัวข้อ 6) |
| "ที่จะขายหรือ email" | ไม่รู้ว่าใครอนุญาตให้ส่งอะไร และไม่มีที่ส่งต่อให้เซลส์ (มิติ 4 · หัวข้อ 9) |

### กติกาเรื่องชื่อและข้อมูล SETA

- SETA ใช้เป็นกรณีอ้างอิงในแผนภายใน · **ฟีเจอร์ทุกชิ้นต้องตอบได้ว่าใช้กับกลุ่มอื่นในหัวข้อ 12 อย่างไร** ถ้าตอบไม่ได้คือของเฉพาะ SETA ไม่ใส่ในผลิตภัณฑ์หลัก
- แผนภายในและการคุยกับ SETA ใช้ชื่อจริงได้
- **ข้อมูลจริงของ SETA เข้าระบบได้หลังเซ็นสัญญาประมวลผลข้อมูล (DPA) เท่านั้น** และอยู่ในบัญชีของ SETA เท่านั้น
- เดโมสาธารณะ เว็บ และสไลด์ขายลูกค้าอื่น ใช้ผู้จัดงานสมมุติ ("Sunline Energy Week — งานสมมุติ")
  จนกว่า SETA ยินยอมเป็นกรณีศึกษาเป็นลายลักษณ์อักษร

## 3 · งานที่ลูกค้าต้องทำ และข้อมูลที่ขาด

ตัวอย่างจากผู้จัดงาน (กลุ่มอื่นมีโครงเดียวกัน ดูหัวข้อ 12) — งานหนึ่งรอบ แต่ละงานต้องการคนคนละกลุ่มจากฐานเดียวกัน:

| งาน | ใครทำ | ต้องการคนแบบไหน | วันนี้ทำยังไง |
|---|---|---|---|
| **ขายบูธ** | ทีมขายบูธ | บริษัทผู้ขายสินค้า/บริการในหมวด ที่มีผู้ตัดสินใจฝ่ายการตลาด/ขายติดต่อได้ | Excel ของเซลส์แต่ละคน |
| **หาสปอนเซอร์** | ผู้บริหาร | บริษัทใหญ่ที่ส่ง VIP หรือวิทยากรมาหลายปี | ความจำคน |
| **ขายตั๋ว/แพ็กเกจสัมมนา** | การตลาด | ผู้จัดการขึ้นไปในหมวดที่ตรงหัวข้อปีนี้ | ส่งทั้งก้อน |
| **เชิญผู้เข้าชม** | การตลาด | ทุกคนที่อนุญาตให้ส่ง และสนใจหมวดนี้ | ส่งทั้งก้อน |
| **เชิญ VIP / วิทยากร** | ผู้บริหาร · โปรแกรม | ระดับ C · ผู้กำหนดนโยบาย · คนที่เคยพูดแล้วคะแนนดี | ความจำคน |
| **รายงานหลังงานให้ผู้ออกบูธ** | ทีมขายบูธ | ผู้เข้าชมที่ยินยอมให้แบ่งข้อมูล | ส่งไฟล์รวม (มักผิด PDPA) |
| **ขายบูธรอบหน้า** | ทีมขายบูธ | ผู้ออกบูธปีนี้ + ผู้ออกบูธเก่าที่หายไป | เริ่มใหม่ทุกปี |

**ข้อสังเกตที่ทำให้แผนนี้ต่างจาก CRM ทั่วไป:** ข้อมูลที่ต้องใช้มีอยู่แล้วเกือบทั้งหมด แค่กระจายอยู่
ลูกค้าไม่ได้ขาดเครื่องมือกรอกข้อมูล — ขาดเครื่องมือ *อ่าน* ข้อมูลที่ตัวเองมี

## 5 · ห้ามิติ

ทุกมิติคำนวณเป็นคอลัมน์จริงที่กรองและนับได้เร็ว (ไม่ใช่ JSON) และทุกค่ามีคำอธิบายว่า "ทำไมได้ค่านี้"

### มิติ 1 · ติดต่อได้ไหม (reachability)

| เกรด | ความหมาย | ตัวอย่างสัญญาณ |
|---|---|---|
| **A** | ติดต่อได้แน่ | อีเมลองค์กร · เปิด/ตอบใน 12 เดือน · ไม่เคยเด้ง |
| **B** | น่าจะได้ | อีเมลองค์กร โดเมนยังรับเมล (มี MX) · เห็นล่าสุดใน 3 ปี |
| **C** | ไม่แน่ | เห็นล่าสุดเกิน 3 ปี · อีเมลกลาง (info@ · sales@) · อีเมลส่วนตัว · มีแต่เบอร์ |
| **D** | ใช้ไม่ได้ | เด้งถาวร · โดเมนตาย · รูปแบบผิด · ขอเลิกรับ · บริษัทปิดกิจการ |

สัญญาณเพิ่ม:
- **น่าจะย้ายงาน** — ชื่อเดียวกันปรากฏกับโดเมนบริษัทใหม่ และโดเมนเดิมเงียบไป → เก็บสังกัดเก่าพร้อมวันสิ้นสุด
  (คนย้ายงานคือโอกาส: ลูกค้าเก่าที่ไปอยู่บริษัทใหม่)
- ตรวจโดเมน **ต่อโดเมน ไม่ใช่ต่ออีเมล** — 100,000 อีเมลมักมีโดเมนแค่หลักพัน ใช้ DNS ธรรมดา
- **ไม่ลองยิงเช็กกับเซิร์ฟเวอร์อีเมล (SMTP probe)** — เสี่ยงโดนบล็อกและไม่แม่นกับ Microsoft 365
  ใช้ผลการส่งจริง (เด้ง · เปิด · ตอบ) ป้อนกลับแทน

### มิติ 2 · เป็นใคร (identity · firmographic)

| ฟิลด์ | ได้มาอย่างไร |
|---|---|
| **ระดับ** | ตำแหน่งไทย/อังกฤษ → ระดับมาตรฐาน: เจ้าของ/ระดับ C · ผู้อำนวยการ/VP · ผู้จัดการ · ผู้ปฏิบัติงาน · ข้าราชการ (ระบุระดับ) · นักวิชาการ · นักศึกษา |
| **สายงาน** | การตลาด · ขาย · วิศวกรรม · จัดซื้อ · บริหาร · การเงิน · นโยบาย · วิจัย |
| **อุตสาหกรรม** | ชุดคำของลูกค้าเอง (ผู้จัดงานพลังงาน: ผู้ผลิตโซลาร์ · ผู้ติดตั้ง · แบตเตอรี่ · EV · การไฟฟ้า/รัฐ · ที่ปรึกษา · การเงิน · ผู้ใช้พลังงานรายใหญ่) |
| **ฝั่งของตลาด** | ผู้ขาย (น่าจะซื้อบูธ) · ผู้ซื้อ (น่าจะเดินงาน) · ผู้กำกับ · สื่อ · วิชาการ |
| **องค์กร** | ชื่อมาตรฐาน · เลขผู้เสียภาษี 13 หลัก (ตรวจ checksum) · สาขา · บริษัทแม่ · ประเทศ · ขนาด · โดเมน |

แปลงตำแหน่งและจัดหมวดด้วยกฎก่อน แล้วใช้ AI กับส่วนที่กฎไม่รู้ (ต่อยอด `lib/engine/ai.ts` + `ai_cache`)
ทุกค่าที่ AI เดามีป้าย "ระบบเดา" จนกว่าคนยืนยัน และแก้ทีเดียวได้ทั้งกลุ่ม (เช่น ทุกคนที่ตำแหน่ง "ผจก.ฝ่ายขาย")

### มิติ 3 · เคยทำอะไรกับเรา (relationship)

| ค่า | ตัวอย่าง |
|---|---|
| ครั้งที่มา · บทบาทที่เคยเป็น | 6 งาน · ผู้เข้าชม → ผู้ออกบูธ → วิทยากร |
| เห็นครั้งแรก / ล่าสุด | 2016 / 2024 |
| มูลค่าที่เคยจ่าย | บูธ 3 ครั้ง รวม ฿540,000 · ตั๋วสัมมนา 2 ครั้ง |
| แบบแผน | **ประจำ** (มาเกือบทุกปี) · **กำลังโต** (มา 2–3 ปีติด) · **หายไป** (เคยมาประจำ ขาด 2 ครั้งล่าสุด) · **ครั้งเดียว** · **ใหม่** |
| ระดับองค์กร | บริษัทนี้ส่งคนมา 14 คนใน 6 ปี · ออกบูธปี 2019 · 2022 · ยังไม่เคยเป็นสปอนเซอร์ |

`lib/engine/derive.ts` คำนวณรอบซื้อและความเสี่ยงหายรายคนอยู่แล้ว → ย้ายไปคำนวณจากการมีส่วนร่วม ทั้งรายคนและรายองค์กร

### มิติ 4 · อนุญาตอะไรไว้ (permission)

แยกตาม **วัตถุประสงค์** ไม่ใช่ "ยินยอม/ไม่ยินยอม" ก้อนเดียว:

| วัตถุประสงค์ | ฐานทางกฎหมายที่เป็นไปได้ (ต้องให้นักกฎหมายยืนยัน) |
|---|---|
| ข่าวสารและเชิญเข้างาน | ความยินยอม |
| ติดต่อเรื่องสัญญาของผู้ออกบูธ/สปอนเซอร์ | สัญญา |
| เสนอขายบูธให้บริษัท | ประโยชน์โดยชอบด้วยกฎหมาย (ต้องประเมิน) |
| **แบ่งข้อมูลผู้เข้าชมให้ผู้ออกบูธ** | **ความยินยอมแยกเฉพาะเรื่องนี้เท่านั้น** |

ต่อคนเก็บ: ฐาน · วันที่ได้ · หลักฐาน (ฟอร์มไหน ไฟล์ไหน) · **เก็บก่อน 1 มิ.ย. 2565 หรือไม่** · วันขอเลิก
คนที่ไม่รู้ฐาน = ส่งไม่ได้ จนกว่าจะผ่านงาน "ขอความยินยอมใหม่" (หัวข้อ 6)

### มิติ 5 · เหมาะกับงานไหน (fit)

คะแนน 0–100 **ต่องาน** (หัวข้อ 6) ไม่ใช่คะแนนรวมก้อนเดียว เพราะคนที่เหมาะกับการขายบูธมักไม่ใช่คนที่ควรได้อีเมลเชิญเดินงาน
คะแนนมาจากกฎที่อ่านได้ทุกข้อ ระยะแรกไม่ใช้โมเดลที่อธิบายไม่ได้ หลังวัดผลได้หลายรอบค่อยให้ระบบปรับน้ำหนักจากผลจริง

### คะแนนสุขภาพฐานข้อมูล

ตัวเลขเดียวต่อบัญชี 0–100 จาก: สัดส่วนเกรด A+B · ความครบของตำแหน่ง/อุตสาหกรรม · สัดส่วนที่รู้ฐาน PDPA ·
อัตราซ้ำที่ยังไม่รวม · ความสดของข้อมูล — แสดงเป็นเส้นตามเวลา เพื่อให้เห็นว่าการดูแลข้อมูลได้ผล

## 6 · Focus (งาน) — ตัวเชื่อมระหว่างข้อมูลกับรายได้

งาน = เป้าหมาย + กฎคัดคน + คะแนน + ปลายทาง ผู้ใช้เลือกจากแม่แบบ แล้วปรับได้

### แม่แบบสำหรับผู้จัดงาน

| แม่แบบ | หน่วยที่คัด | ปลายทาง |
|---|---|---|
| ขายบูธ | องค์กร | ท่อขาย แจกเซลส์ |
| หาสปอนเซอร์ | องค์กร | ท่อขาย ผู้บริหาร |
| ขายตั๋ว/แพ็กเกจสัมมนา | คน | อีเมล + กลุ่มควบคุม |
| เชิญผู้เข้าชม | คน | อีเมล + กลุ่มควบคุม |
| เชิญ VIP / วิทยากร | คน | รายชื่อให้ผู้บริหารโทร |
| ขอความยินยอมใหม่ | คน | อีเมลขอยืนยัน → อัปเดตมิติ 4 |
| ดึงผู้ออกบูธเก่ากลับ | องค์กร | ท่อขาย |
| ติดตามคนย้ายงาน | คน | ท่อขาย (บริษัทใหม่) |
| ล้างข้อมูล | คน | คิวตรวจ (ซ้ำ · ขาดตำแหน่ง · เกรด D) |

### ตัวอย่างกฎ: ขายบูธ Powerverse 2026

| เงื่อนไข | คะแนน |
|---|---|
| เคยออกบูธ แต่ขาด 1–2 ครั้งล่าสุด | +40 |
| ฝั่งตลาด = ผู้ขาย ในหมวดที่ตรงธีมปีนี้ | +20 |
| ส่งคนมาเดินงาน ≥ 2 ปีติด แต่ไม่เคยออกบูธ | +15 |
| มีผู้ติดต่อระดับผู้จัดการขึ้นไป ฝ่ายการตลาด/ขาย เกรด A–B | +15 |
| องค์กรโตขึ้น (ส่งคนมามากขึ้นปีต่อปี) | +10 |
| **ตัดออก:** มีดีลเปิดอยู่ · ถูกปฏิเสธใน 90 วัน · ไม่มีผู้ติดต่อเกรด A–C เลย | |

ผลเป็นรายชื่อองค์กรเรียงคะแนน ทุกแถวมีป้ายเหตุผล ("เคยออกบูธ 2019 · 2022 · หายไป 2 งาน · มี ผจก.การตลาดติดต่อได้")
กดส่งเข้าท่อขาย → แจกเซลส์แบบวนหรือตามหมวด

### ตัวอย่างกฎ: เชิญผู้เข้าชม

มิติ 4 อนุญาต "ข่าวสาร" · เกรด A–B · สนใจหมวดที่ตรงธีม · ยังไม่ลงทะเบียนปีนี้ · ไม่ได้รับอีเมลจากเรา 7 วันล่าสุด
→ กันกลุ่มควบคุม 10% **แบบสุ่มทั้งองค์กร** (หัวข้อ 11) → ส่ง → วัดว่าลงทะเบียนเพิ่มเท่าไร

## 7 · ชุดจัดการฐานข้อมูลและหน้าจอ

ผลิตภัณฑ์แบ่งเป็นสามชั้น — **ชั้นข้อมูลคือหัวใจ** ชั้นใช้งานคือที่มาของรายได้ ชั้นควบคุมคือสิ่งที่ทำให้องค์กรกล้าฝากข้อมูล

### ชั้นข้อมูล (Data) — "บริหาร database"

| โมดูล | ทำอะไรได้ | ตอบปัญหา |
|---|---|---|
| **Sources** | ลากหลายไฟล์ (xlsx · csv · หลายชีต) · ป้ายโปรแกรม/ครั้ง/บทบาทต่อไฟล์ · แม่แบบจับคู่คอลัมน์ที่จำไว้ · **ลำดับความน่าเชื่อถือของแหล่ง** (ไฟล์สัญญา > ไฟล์ลงทะเบียน > ไฟล์ฟอร์มเว็บ) · กันไฟล์ซ้ำ · ยกเลิกทั้งชุดนำเข้าได้ · (ภายหลัง) ดึงอัตโนมัติจาก Google Sheets/SFTP/API | "ข้อมูลกระจาย" |
| **Golden Record** | รวมคน/องค์กรด้วยชุดกฎที่ตั้งได้ (หัวข้อ 8) · เลือกค่าต่อฟิลด์ด้วยกฎ · ล็อกค่าที่คนยืนยัน · แยกออก (unmerge) ได้ · บริษัทแม่/สาขา | "จัดการยังไง" |
| **Clarity** | คะแนนความคมชัดรวมและรายมิติ · ตามแหล่ง ตามทีม ตามเวลา · **เป้าคุณภาพ (data SLA)** เช่น "เกรด D ในลูกค้าปัจจุบันไม่เกิน 5%" แจ้งเตือนเมื่อหลุด · ปัญหา 10 อันดับพร้อมปุ่มแก้ | "ไม่รู้อันไหนใช้ได้" |
| **Calibrate** | คิวงานผู้ดูแลข้อมูล: คู่ที่ไม่แน่ใจ · ป้ายที่ระบบเดา · ค่าผิดกฎ · มอบหมายคนดูแล · ปุ่มลัดคีย์บอร์ด · ตัดสินครั้งเดียวใช้กับทั้งกลุ่ม | "ใครดูแลข้อมูล" |
| **Trace** | ที่มาของทุกค่า · ประวัติการแก้ทุกฟิลด์ · ย้อนดูเรคคอร์ด ณ วันใดก็ได้ · กู้ค่าเดิม | "เชื่อข้อมูลได้ไหม" |
| **Schema** | ฟิลด์กำหนดเอง (ข้อความ · ตัวเลข · เงิน · วันที่ · ตัวเลือก · หลายตัวเลือก) · ชุดคำแบบลำดับชั้น (อุตสาหกรรม → หมวดย่อย) · ฟิลด์คำนวณ · กฎตรวจค่า · ชนิดเรคคอร์ด | "ข้อมูลไม่เป็นมาตรฐาน" |
| **Bulk Change** | แก้/ติดป้าย/รวม/ลบทีละหลายพันเรคคอร์ด **ดูผลก่อนกด** · ทุกชุดย้อนกลับได้ · ชุดใหญ่ต้องมีคนอนุมัติ | "แก้ทีละแถวไม่ไหว" |
| **Rule Lab** | แก้กฎรวมคน / เลือกค่า / ตรวจ / มิติ แล้วรันบนสำเนา → "การรวม 1,240 คู่จะเปลี่ยน · เกรด B → C 3,100 คน" → ใช้จริงหรือทิ้ง | "กลัวแก้แล้วพัง" |

### ชั้นใช้งาน (Activate) — ทำให้ฐานข้อมูลเป็นรายได้

| โมดูล | ทำอะไรได้ |
|---|---|
| **Golden Record ของคน/องค์กร** | Depth ห้ามิติ · ไทม์ไลน์บทบาท 10 ปี · ประวัติสังกัด · ดีลและกิจกรรม · Trace ทุกค่า · สรุปโดย Steward |
| **Programs** | แบรนด์และครั้ง · คนกลับมาปีต่อปี · การย้ายบทบาท (ผู้เข้าชม → ผู้ออกบูธ) |
| **Prism** | ตารางไขว้ทุกมิติ (รวมมิติคุณภาพ) · กดช่องได้รายชื่อ · ถามเป็นภาษาไทยผ่าน Steward ("ผู้จัดการสายโซลาร์ที่หายไป 2 ปีมีกี่คน") |
| **Lens** | มุมมองที่บันทึก · นับใหม่เอง · มีเจ้าของ วัตถุประสงค์ และการแชร์ · แจ้งเมื่อจำนวนเปลี่ยนมาก |
| **Focus** | แม่แบบงาน → คะแนนพร้อมเหตุผล → ท่อขายหรืออีเมล (หัวข้อ 6) |
| **Pipeline** | ดีลต่อครั้งของโปรแกรม · ขั้น · Kanban · เป้า · กิจกรรมและงานที่ต้องทำ |
| **Email** | ส่งจากโดเมนลูกค้า · ตัดคนอัตโนมัติ · warm-up · กลุ่มควบคุมทั้งองค์กร · ผลวัดได้ (หัวข้อ 9, 11) |
| **Triggers** | เมื่อมิติ/ค่าเปลี่ยน → สร้างงาน · แจ้งเจ้าของ · ย้ายเข้า Lens · เรียก webhook |
| **Executive** | Relationship Equity · Clarity · ท่อขายจาก Focus · ผลที่วัดได้ · รายงานไตรมาส (PDF) |

### ชั้นควบคุม (Govern) — สิ่งที่ฝ่าย IT และกฎหมายถาม

| โมดูล | ทำอะไรได้ |
|---|---|
| **Consent Ledger** | ฐาน PDPA ต่อคนต่อวัตถุประสงค์ · หลักฐาน · ประวัติแก้ย้อนหลังไม่ได้ · คำขอเจ้าของข้อมูล (ดู · สำเนา · ลบ · เลิก) เป็นงานที่ติดตามได้ |
| **Access** | บทบาท · ขอบเขตการเห็น (ของตัวเอง/ทีม/ทั้งหมด) · ซ่อนฟิลด์ตามบทบาท · โอนพอร์ต · SSO · 2FA |
| **Audit** | ใครเปิด/แก้/ส่งออกอะไรเมื่อไร · บันทึกการตั้งค่า · การเปิดค่าจริงทีละค่า (มีแล้ว) |
| **Retention** | นโยบายเก็บข้อมูลต่อบัญชี · คิวทบทวนก่อนลบ · ลบถึงแถวดิบ |
| **Platform** | REST + bulk API · webhook · ส่งออกตามรอบไป Google Sheets / BigQuery / S3 ("ข้อมูลของคุณ ไม่ถูกขัง") |

### เมนู

```
ภาพรวม (Clarity + Equity)
ข้อมูล    Sources · People · Orgs · Programs · Calibrate · Schema · Rule Lab
ใช้งาน    Prism · Lens · Focus · Pipeline · Email · Triggers
ควบคุม    Consent · Access · Audit · Platform
          Steward (แผงข้างทุกหน้า)
```

หน้าลูกค้า ค้นหา รวมซ้ำ ส่งออก ที่ทำไว้แล้วคือโครงตั้งต้นของหน้า **People** และ Golden Record ของคน

## 8 · การรวมคนซ้ำ (identity resolution)

หัวใจของ "จัดการยังไง" — ถ้าข้อนี้ผิด ทุกมิติผิดตาม

### คีย์จับคู่ (เรียงตามความมั่นใจ)

| คีย์ | ผล |
|---|---|
| อีเมลส่วนบุคคลตรงกัน (HMAC เดิมใน `contact_points`) | รวมอัตโนมัติ |
| เบอร์มือถือตรงกัน | รวมอัตโนมัติ ถ้าชื่อไม่ขัดกัน |
| ชื่อ (ปรับรูปแล้ว) + องค์กร (ปรับรูปแล้ว) ตรงกัน | รวมอัตโนมัติ |
| ชื่อคล้าย + โดเมนอีเมลเดียวกัน | คิวตรวจ |
| ชื่อตรง + องค์กรต่าง | คิวตรวจ (อาจเป็นคนย้ายงาน) |
| **อีเมลกลาง** (info@ · sales@ · admin@) | **ไม่ใช่คีย์ของคน** — ผูกกับองค์กรแทน |

### การปรับรูป (normalisation)

- ชื่อคน: ตัดคำนำหน้า (คุณ · นาย · นาง · นางสาว · ดร. · Mr. · Ms. · Dr. · ผศ. · รศ.) · ช่องว่างไทย · สะกดอังกฤษหลายแบบ (Somchai/Somchay) · สลับชื่อ-นามสกุล
- องค์กร: ตัด "บริษัท … จำกัด (มหาชน)" · "บจก." · "Co., Ltd." · "PCL" · "Public Company Limited" · ไทย ↔ อังกฤษจับคู่ด้วยโดเมนหรือเลขผู้เสียภาษี
- โดเมนอีเมล → องค์กร (ยกเว้นโดเมนฟรี gmail · hotmail · outlook · yahoo)

### ชุดกฎที่ลูกค้าตั้งได้ (ระดับเดียวกับ identity resolution ของ Salesforce Data 360)

- **กฎจับคู่ (match rules)** — หลายกฎต่อชุด แต่ละกฎระบุฟิลด์และวิธี: ตรงตัว · ปรับรูป · คล้าย (พร้อมเกณฑ์)
  ค่าตั้งต้นคือตารางคีย์ด้านบน · ลูกค้าเพิ่มได้ เช่น "รหัสสมาชิกตรงกัน = คนเดียวกัน"
- **กฎเลือกค่า (survivorship)** ต่อฟิลด์: ล่าสุด · พบบ่อยที่สุด · ตามลำดับความน่าเชื่อถือของแหล่ง · คนล็อกไว้ (ชนะเสมอ)
  ตัวอย่าง: ตำแหน่ง = ล่าสุด · ชื่อบริษัท = แหล่งสัญญาก่อน · เลขผู้เสียภาษี = แหล่งสัญญาเท่านั้น
- **ระดับความเข้ม** เป็นการตัดสินใจทางธุรกิจ — หลวมขึ้นได้คนมากขึ้นแต่เสี่ยงรวมผิด → แก้ใน Rule Lab เห็นผลต่างก่อนใช้
- ทุกกฎเป็นข้อมูลในตาราง ไม่ใช่โค้ด — แบบเดียวกับแม่แบบงาน

### กติกา

- รวมแล้ว **ไม่ลบแถวดิบ** — บันทึกว่ารวมเมื่อไร ด้วยกฎไหน ใครยืนยัน · ยกเลิกได้
- ค่าที่ขัดกัน เลือกด้วยกฎเลือกค่าของฟิลด์นั้น เก็บค่าอื่นไว้ใน Trace
- **วัดความแม่นได้จริง**: ตัวสร้างข้อมูลเดโมรู้ว่าแถวไหนเป็นคนเดียวกัน → ทดสอบ precision ≥ 98% · recall ≥ 90% ทุกครั้งที่แก้กฎ

## 9 · อีเมล

สำหรับ B2B **อีเมลมาก่อน LINE** — การเชิญงาน การขายบูธ และใบเสนอราคาวิ่งบนอีเมล

| เรื่อง | แผน |
|---|---|
| ผู้ให้บริการส่ง | Amazon SES · Postmark · Resend — เลือกในระยะ 4 (ต้นทุนต่อพันฉบับ · ส่งจากโตเกียว/สิงคโปร์ได้ · webhook เด้ง/ร้องเรียน) |
| โดเมนผู้ส่ง | ส่งในนามโดเมนของลูกค้า · ตั้ง SPF · DKIM · DMARC ให้ครบก่อนส่งฉบับแรก |
| กติกาผู้ส่งจำนวนมากของ Gmail/Yahoo (ตั้งแต่ 2024) | ยืนยันตัวตนโดเมน · ลิงก์เลิกรับคลิกเดียว · อัตราถูกแจ้งสแปมต่ำกว่า 0.3% |
| **รายชื่อเก่า 10 ปี** | ห้ามส่งทั้งก้อน: เริ่มที่เกรด A → B ทีละขั้น (warm-up) · เด้งเกินเกณฑ์ หยุดอัตโนมัติ |
| ตัดคนออกอัตโนมัติ | เด้งถาวร · เลิกรับ · ร้องเรียน · ไม่มีฐาน PDPA · เกินเพดานความถี่ |
| ผลป้อนกลับ | เด้ง → มิติ 1 · เลิกรับ → มิติ 4 · เปิด/คลิก/ตอบ → มิติ 1 และ 3 |

## 11 · วัดผล

เครื่องวัดแบบกันกลุ่ม (`lib/engine/proof.ts`) **กลับมามีความหมายเต็มที่** เพราะอีเมลเชิญงานส่งถึงคนหลักพันถึงหมื่น
และตัวชี้วัดเป็นแบบสองค่า (ลงทะเบียน/ไม่ลงทะเบียน · ซื้อบูธ/ไม่ซื้อ) ซึ่ง `proof.ts` ใช้อยู่แล้ว

ต้องเปลี่ยนสองเรื่อง:

1. **สุ่มทั้งองค์กร** — ถ้าคนหนึ่งในบริษัทได้อีเมล อีกคนอยู่กลุ่มควบคุม อีเมลจะถูกส่งต่อกันในบริษัท กลุ่มควบคุมเสีย
   `armFor` ตอนนี้ hash `customer_id + campaign_id` → เปลี่ยนเป็น hash `org_id + campaign_id` (คนไม่มีองค์กรใช้ตัวเอง)
   ช่วงความเชื่อมั่นคำนวณแบบ bootstrap ทีละองค์กร
2. **ผลลัพธ์มาจากการนำเข้า** — รายชื่อผู้ลงทะเบียน/ผู้ซื้อบูธนำเข้าเป็นการมีส่วนร่วม แล้วจับกับกลุ่มที่ส่ง/ไม่ส่ง

งานขายบูธมีองค์กรหลักร้อย → ระบบบอกตรง ๆ ว่า "ยังวัดไม่ได้" (มีอยู่แล้ว) และรายงานเป็นอัตราปิดดีลแทน

## 12 · กลุ่มลูกค้า

โครง **คน · องค์กร · โปรแกรม · บทบาท · การมีส่วนร่วม** ใช้ซ้ำได้ เปลี่ยนแค่คำเรียกและแม่แบบงาน
ทุกกลุ่มต้องผ่านเกณฑ์ ICP (หัวข้อ 1.1) — ตารางนี้คือที่ที่หาลูกค้าที่ผ่านเกณฑ์ ไม่ใช่รายชื่อที่จะขายทุกราย

| กลุ่ม | "โปรแกรม" | บทบาท | งานหลัก | ทำไมเหมาะ |
|---|---|---|---|---|
| **ผู้จัดงานแสดงสินค้า/สัมมนา** | งาน → ครั้ง | ผู้เข้าชม · ผู้ออกบูธ · วิทยากร · VIP · สปอนเซอร์ | ขายบูธ · เชิญเข้างาน · สปอนเซอร์ | ฐานใหญ่ หลายแบรนด์ หลายปี วัดผลชัด |
| **สมาคมการค้า · หอการค้า** | ปีสมาชิก · คณะกรรมการ · กิจกรรม | สมาชิก · กรรมการ · ผู้ร่วมกิจกรรม · สปอนเซอร์ | ต่ออายุสมาชิก · หาสมาชิกใหม่ · สปอนเซอร์ | รายได้ผูกกับการต่ออายุ ข้อมูลกระจายตามคณะกรรมการ |
| **หลักสูตรอบรม · หลักสูตรผู้บริหาร** | หลักสูตร → รุ่น | ผู้เรียน · ศิษย์เก่า · วิทยากร · บริษัทที่ส่งคนมาเรียน | ขายหลักสูตรถัดไปให้ศิษย์เก่า · ขายอบรมในองค์กร | ศิษย์เก่าหลักหมื่น ไม่มีใครดูแลต่อ |
| **สื่อ B2B · สำนักพิมพ์ · พอดแคสต์** | ฉบับ · ซีรีส์ · งานสัมมนา | สมาชิก · ผู้ลงโฆษณา · ผู้ให้สัมภาษณ์ | ขายโฆษณา · ขายงาน | ผู้อ่านคือฐานผู้ซื้อของผู้ลงโฆษณา |
| **ผู้ผลิต · ผู้นำเข้า · ตัวแทนจำหน่าย** | สายสินค้า · โครงการ · โปรแกรมดีลเลอร์ | ดีลเลอร์ · ผู้ติดตั้ง · เจ้าของโครงการ · ผู้ใช้ปลายทาง | สั่งซ้ำ · ขายข้ามสาย · หาดีลเลอร์ใหม่ | มียอดสั่งซ้ำ ใช้รอบสั่งซื้อ (มิติ 3) ได้เต็ม |
| **บริษัทรับจ้างงานโครงการ** (เอเจนซี · สตูดิโอ · ที่ปรึกษา) | โครงการ · pitch | ผู้ว่าจ้าง · ผู้ประสานงาน · พันธมิตร | ขายงานซ้ำ · ตามคนย้ายบริษัท | คนในวงการย้ายงานบ่อย ความสัมพันธ์ตามคน ไม่ตามบริษัท |

**ใช้เองก่อน (dogfood):** ORIONS เป็นกลุ่มสุดท้ายในตารางพอดี — ฐานลูกค้า ผู้ประสานงาน และพันธมิตรของ ORIONS
ทดลองบนระบบได้โดยไม่ต้องรอลูกค้าภายนอก (ถ้าเจ้าของต้องการ)

**ไม่รับ:** พรรคการเมือง การหาเสียง การยิงเป้าผู้มีสิทธิ์เลือกตั้งรายบุคคล — บัญชีพรรคในเดโมถูกถอดออกในระยะ 0

ลำดับเจาะตลาด: **ผู้จัดงาน → สมาคม → หลักสูตรอบรม** (ทั้งสามมีโครงคล้ายกันที่สุด แม่แบบงานใช้ข้ามกันได้มาก)
**ตั้งแต่หมุด M2 เดโมต้องมีอย่างน้อยสองกลุ่ม** (ผู้จัดงาน + ตัวแทนจำหน่าย B2B) เพื่อพิสูจน์ว่าไม่ได้สร้างมาเพื่อผู้จัดงานรายเดียว

### นำร่องกับลูกค้ารายแรก (ทางเลือก ขนานกับระยะ 1–2)

ลูกค้านำร่องคือใครก็ได้ที่ผ่าน ICP — SETA เป็นตัวเลือกที่ชัดที่สุดเพราะเห็นปัญหาแล้ว
ตัวอย่างด้านล่างใช้ Powerverse Thailand (**26 พ.ย. 2026**) ซึ่งทำได้ถ้าได้ไฟล์ภายในราว 20 ต.ค.
ลูกค้านำร่องรายอื่นใช้ขั้นตอนเดียวกันกับรอบงาน/รอบขายของเขา:

| สัปดาห์ 2–3 | สแกนสุขภาพบนข้อมูลจริง (ใช้ตัวนำเข้าและการรวมซ้ำที่มีอยู่ + ส่วนแรกของระยะ 1) · ส่งรายงานให้ SETA |
| สัปดาห์ 3 | คัด "เชิญเข้าชม Powerverse" + กันกลุ่มควบคุม 10% แบบทั้งองค์กร → **ส่งออกให้ SETA ส่งด้วยเครื่องมือเดิม** |
| หลังงาน | นำเข้ารายชื่อผู้ลงทะเบียน/ผู้มางาน → รายงาน "อีเมลที่คัดแล้วทำให้ลงทะเบียนเพิ่มเท่าไร" |

## 20 · ความเสี่ยง

- **คุณภาพการรวมคนซ้ำ** — รวมผิดคนครั้งเดียว ลูกค้าเลิกเชื่อทั้งระบบ → รวมอัตโนมัติเฉพาะคีย์แน่น ที่เหลือเข้าคิว · ยกเลิกได้ · วัดด้วยข้อมูลมีเฉลยทุกครั้ง
- **ส่งอีเมลรายชื่อเก่าแล้วโดเมนลูกค้าเสียชื่อ** — ความเสียหายตกที่ลูกค้า → warm-up บังคับ · หยุดอัตโนมัติ · เริ่มด้วยการส่งออกให้ลูกค้าส่งเอง
- **PDPA** — ข้อมูล 10 ปีส่วนใหญ่ไม่มีหลักฐานความยินยอม → มิติ 4 ต้องตรงไปตรงมาว่า "ส่งได้" น้อยกว่าที่ลูกค้าหวัง และขายงานขอความยินยอมใหม่เป็นทางออก
- **ข้อมูลลูกค้าทั้งบริษัทอยู่ในระบบที่คนพัฒนาคนเดียวดูแล** — ต้องมีการสำรอง กู้คืนที่ทดสอบแล้ว และบันทึกการเข้าถึงก่อนรับลูกค้ารายที่สอง
- **รอบขายองค์กรยาว** — นำร่องรายแรกคือหลักฐานที่ต้องมี ก่อนลงแรงกับเว็บและราคา
- **ลูกค้าน้อยราย = เสียหนึ่งรายเจ็บมาก** — premium ต้องส่งมอบระดับ premium จริง: ผลสแกนสัปดาห์แรก · ทบทวนรายไตรมาส · ตอบเร็ว
- **ติดกับลูกค้ารายแรก** — ถ้าทำตามคำขอของรายแรกทุกข้อ ผลิตภัณฑ์จะกลายเป็นงานจ้างทำ → กฎในหัวข้อ 2: ทุกฟีเจอร์ต้องใช้กับกลุ่มอื่นได้
- **ขอบเขตบาน** — ทุกกลุ่มลูกค้าจะขอของเฉพาะตัว → แม่แบบงานเป็นข้อมูล ไม่ใช่โค้ด (หลักเดียวกับคลัง play เดิม)

## 21 · ตั้งใจไม่ทำ

- ขายหรือซื้อข้อมูลรายชื่อจากภายนอก — ทำงานกับข้อมูลของลูกค้าเท่านั้น
- ลองยิงเช็กอีเมลกับเซิร์ฟเวอร์ผู้รับ
- ระบบลงทะเบียนงาน · ผังบูธ · ขายตั๋วหน้างาน — เชื่อมกับระบบที่ลูกค้าใช้แทน (นำเข้า/API)
- custom object · เขียนโค้ดบนแพลตฟอร์ม · แอปมือถือ ในรอบแรก
- งานการเมืองทุกรูปแบบ
- แผนฟรี · สมัครเองโดยไม่ได้คุย · ลูกค้าที่ไม่ผ่าน ICP
- ปรับแต่งเฉพาะรายที่ใช้กับลูกค้ารายอื่นไม่ได้
- AppExchange · ภาษาโปรแกรมบนแพลตฟอร์ม (แบบ Apex) · งานบริการลูกค้า (Service) · CPQ · territory · marketing automation เต็มรูป
- AI ที่แก้ข้อมูลเองโดยไม่มีคนอนุมัติ
