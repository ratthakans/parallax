## 1 · หลักวิศวกรรม 11 ข้อ

1. **แถวดิบเป็นความจริงเดียว ทุกอย่างที่เหลือสร้างใหม่ได้**
   `source_rows` ไม่ถูกแก้หรือลบ (ยกเว้นลบตามคำขอ PDPA) · Golden Record · มิติ · คะแนน สร้างใหม่ทั้งบัญชีได้ด้วย `rebuildTenant()`
2. **การตัดสินใจของคนแยกจากผลของเครื่อง และชนะเสมอ**
   รวม/ไม่รวม (`resolution_overrides`) · ค่าที่ยืนยัน (`field_locks`) · ป้ายที่แก้ (`label_overrides`) — rebuild เคารพทั้งหมด
3. **กฎทุกชนิดเป็นข้อมูล ไม่ใช่โค้ด**
   กฎจับคู่ · กฎเลือกค่า · กฎตรวจ · เกณฑ์มิติ · แม่แบบ Focus · Triggers เก็บในตาราง ลูกค้าแก้ได้ ทดลองได้ใน Rule Lab
4. **ทุกค่าตอบได้ว่ามาจากไหน (Trace)**
   ค่าบน Golden Record ชี้กลับแถวดิบ + กฎที่เลือกมัน · ทุกการเปลี่ยนลง `field_history` แบบเพิ่มอย่างเดียว → ย้อนดู ณ วันใดก็ได้
5. **ทุกการเปลี่ยนจำนวนมากย้อนกลับได้**
   Bulk Change · นำเข้าทั้งชุด · ใช้กฎใหม่ ทุกอย่างเป็น change set ที่มีตัวอย่างก่อนกดและปุ่มย้อนกลับ
6. **มิติเป็นคอลัมน์จริง มี index · คำนวณใน SQL** — ไม่ใส่ค่าที่ต้องกรอง/นับไว้ใน JSON
7. **ID กำหนดได้ (deterministic)** — ต่อยอด `customerIdFor()` ใน `pii.ts` · rebuild แล้ว ID เดิม ดีลและบันทึกไม่หลุด
8. **สองฐานข้อมูลยังตรงกัน** — SQLite (เครื่องพัฒนา · CI · เดโม) และ Postgres (production) · `verify:schema` ครอบตารางใหม่อัตโนมัติ ·
   จับชื่อคล้ายทำใน JS ภายในบล็อกเล็ก จึงไม่ต้องพึ่ง `pg_trgm`
9. **ไม่มีโค้ดเฉพาะลูกค้ารายใด** — `boundaries.mts` ห้ามชื่อลูกค้าจริงหรือ tenant id จริงในโค้ด · ทุกฟีเจอร์ทดสอบบนข้อมูลสมมุติอย่างน้อยสองกลุ่ม (ตั้งแต่สปรินต์ 7)
10. **มาตรฐาน premium เป็นเกณฑ์ที่วัดได้** — งบเวลาหน้า (< 1 วินาที) วัดใน CI · axe ทุกหน้า · รีวิวภาพหน้าจอก่อนปิดสปรินต์ ·
    ไม่มีหน้า "กำลังสร้าง" ถึงลูกค้า · ข้อความผิดพลาดบอกว่าเกิดอะไรและทำอะไรต่อได้
11. **AI เสนอ คนอนุมัติ และ AI ไม่เห็นค่าจริงของช่องทางติดต่อ**
    ทุกคำขอผ่าน AI Gateway จุดเดียว (`lib/engine/ai/` — PII guard · งบ · ledger) · `boundaries.mts` ห้ามเรียก SDK ที่อื่น ·
    Steward ได้แค่ข้อมูลที่จำเป็น (ชื่อตำแหน่ง ชื่อองค์กร ค่าที่ปิดบาง) · ผลลัพธ์เป็นโครงสร้างที่ตรวจด้วย schema ก่อนใช้ ·
    ไม่สร้าง SQL เอง — แปลงคำถามเป็นคำสั่ง Prism ที่ตรวจได้ · ไม่แก้ข้อมูลเองไม่ว่ากรณีใด

## 2 · สถาปัตยกรรม

```
             ┌───────────────────────── ชั้นข้อมูล (Data) ─────────────────────────┐
 ไฟล์/ระบบ ─▶ ① Sources     source_files · source_rows (เข้ารหัส) · แม่แบบ · ลำดับแหล่ง
             │      ▼
             │   ② Stage       ปรับรูปชื่อ/องค์กร/อีเมล/เบอร์/ตำแหน่ง/วันที่ → candidate
             │      ▼
             │   ③ Resolve     match_rules → บล็อก → คะแนน → กลุ่ม + resolution_overrides → merge_log
             │      ▼
             │   ④ Survive     survivorship_rules + source_priority + field_locks → ค่าของ Golden Record
             │      ▼                                                    └─▶ field_history (Trace)
             │   ⑤ Materialise customers · orgs · affiliations · contact_points · participations · custom_values
             │      ▼
             │   ⑥ Derive      มิติ 1–4 · Clarity · data SLA · validation → Calibrate
             └────────────────────────────────────────────────────────────────────┘
                    ▼
             ┌──────────────── ชั้นใช้งาน (Activate) ────────────────┐
             │   Prism · Lens · Focus (มิติ 5) → Pipeline / Email      │
             │   Triggers ◀── เมื่อมิติหรือค่าเปลี่ยน                     │
             └──────────────────────┬────────────────────────────────┘
                                    ▼
             ⑦ Signals    email_events · ผลที่นำเข้ากลับ · ดีลได้/แพ้ ──▶ กลับไปที่ ⑥

  Rule Lab  = รัน ③–⑥ ลงตาราง lab_* ด้วยกฎฉบับร่าง แล้ว diff กับของจริง · ไม่แตะตารางจริง
  Govern    = RLS ตาม tenant + ขอบเขตตามบทบาท/ทีม/เจ้าของ + ซ่อนฟิลด์ + access_log ครอบทุกชั้น
```

### คิวงานเบื้องหลัง

| | |
|---|---|
| ตาราง | `work_queue` (id · tenant_id · kind · payload · state · progress · attempts · locked_until · error) — ไม่ใช้ชื่อ `jobs` เพราะชนกับ Focus |
| ตัวเดิน | `POST /api/work/step` ทำหนึ่งก้อนในงบ ~20 วินาที แล้วคืนความคืบหน้า |
| ใครเรียก | หน้าที่รอผลเรียกต่อเนื่อง + cron เป็นตาข่าย (T2) |
| ทนพัง | ล็อกด้วย `locked_until` · ทำซ้ำได้ · ก้อนที่พัง 3 ครั้งหยุดและแสดงเหตุผล |

### Trace และย้อนเวลา

- ค่าปัจจุบันอยู่บนตารางหลัก (อ่านเร็ว) · ทุกการเปลี่ยนลง `field_history` (เพิ่มอย่างเดียว) พร้อมสาเหตุ: นำเข้า · กฎ · คน · Bulk Change · Trigger
- "ณ วันที่ X" = ค่าปัจจุบันย้อนด้วย history หลัง X · ค่า PII ใน history เก็บแบบปิดบาง (ค่าจริงอยู่ที่แถวดิบที่เข้ารหัส)

### ฟิลด์กำหนดเอง

`custom_values` แยกคอลัมน์ตามชนิด (`v_text` · `v_num` · `v_date` · `v_bool` · `v_option`) มี index ต่อ (tenant, field, ค่า)
→ Prism และ Lens กรอง/นับฟิลด์กำหนดเองได้เร็วเท่าฟิลด์ระบบ (ข้อตัดสินใจ T8)

## 7 · นำร่องกับลูกค้ารายแรก (สาย F)

ขนานกับสปรินต์ · **ไม่มีสปรินต์ไหนรอสายนี้** · ลูกค้านำร่องคือใครก็ได้ที่ผ่าน ICP — ในทางปฏิบัติคือ Database Audit รายแรก

| | เมื่อ | อะไร | ใช้ของจาก |
|---|---|---|---|
| **F0** | เมื่อพร้อม | DPA · รับไฟล์ · ประชุม 1 ชม. ระบุโปรแกรม/ปี/บทบาทของแต่ละไฟล์ · สร้างบัญชีลูกค้า (`is_customer`) | สปรินต์ 0 |
| **F1** | ถ้ามีรอบอีเมลเร่งด่วน | รวมด้วยคีย์แน่น · เกรดขั้นต้น · คัดรายชื่อ + กลุ่มควบคุมทั้งองค์กร → ส่งออกให้ลูกค้าส่งด้วยเครื่องมือเดิม | สปรินต์ 1 |
| **F2** | หลัง 29 พ.ย. | **Database Audit เต็ม**: Golden Record · Clarity · ปัญหา · งานที่ทำเงินได้ทันที · นำเสนอผู้บริหาร | สปรินต์ 2–3 |
| **F3** | หลังรอบงาน/รอบขาย | นำเข้าผลลัพธ์ → รายงานเทียบกลุ่มควบคุม · เสนอสัญญารายปี | สปรินต์ 5 (นำเข้าผล) |

ตัวอย่างที่ชัดที่สุดตอนนี้: SETA กับ Powerverse Thailand 26 พ.ย. 2026 — F1 ทันถ้าได้ไฟล์ภายในราว 20 ต.ค.

ข้อมูลจริงของลูกค้าอยู่ในบัญชีของลูกค้านั้นบน production เท่านั้น — ไม่ดาวน์โหลดลงเครื่องพัฒนา ไม่ใช้ในชุดทดสอบ
สิ่งที่เรียนจากข้อมูลจริง (รูปแบบความยุ่งใหม่) กลับไปเพิ่มในตัวสร้างข้อมูลสมมุติ ไม่ใช่คัดลอกข้อมูล

## 9 · การ deploy และข้อมูล production

- deploy ทุกหมุด และเมื่อลูกค้านำร่องต้องใช้ · วิธีเดิม: สำเนาสะอาดไม่มี `.env*` → `vercel deploy --prod`
- migration ใช้กับ Supabase ก่อน deploy โค้ดที่ต้องใช้มันเสมอ
- production ตอนนี้มีแค่ข้อมูลเดโมสังเคราะห์ + บัญชีผู้ใช้ → สปรินต์ 0 ล้างบัญชีเดโมค้าปลีก/พรรคบน Supabase ได้โดยไม่ต้องย้ายข้อมูล
  (เป็นการลบบน production — ทำเมื่อเจ้าของยืนยันในตอนนั้น) · `tenant_users` และ `contact_leads` คงไว้
- `PII_HMAC_KEY` ห้ามเปลี่ยน — ID ที่กำหนดได้และการจับคู่ทั้งหมดขึ้นกับมัน
- บัญชีสมมุติสร้างใหม่ได้ทุกเมื่อด้วย seed คงที่ · บัญชีลูกค้าจริง (`is_customer`) ไม่ถูก seed หรือล้างโดยสคริปต์ใดเลย

## 11 · ความเสี่ยงทางเทคนิค

| ความเสี่ยง | ผลกระทบ | รับมือ |
|---|---|---|
| ข้อมูลจริงยุ่งกว่าตัวสร้าง | precision บนข้อมูลจริงต่ำกว่าที่วัด | สุ่มตรวจ 200 คู่ทุกครั้งที่นำเข้าข้อมูลจริง · ส่วนต่างกลับไปเพิ่มในตัวสร้าง |
| กฎที่ลูกค้าตั้งเองหลวมเกิน | รวมผิดคนจำนวนมาก | ต้องผ่าน Rule Lab ก่อนใช้จริง · เกินเกณฑ์ต้องผู้ดูแลอนุมัติ · ย้อนกลับได้ |
| `field_history` โตเร็ว | พื้นที่ · ความเร็ว | เก็บเฉพาะการเปลี่ยนจริง · บีบอัดชุดนำเข้าเป็นหนึ่งเหตุการณ์ต่อชุด · index ตาม (tenant, record, at) |
| Rule Lab บนฐานใหญ่ช้า/แพง | ลูกค้ารอนาน | รันในคิว · จำกัดหนึ่งงานต่อบัญชี · ตัวเลือกทดลองบนตัวอย่าง 10% ก่อน |
| ตารางค่าฟิลด์กำหนดเองช้าเมื่อไขว้หลายฟิลด์ | Prism ช้า | index ต่อ (tenant, field, ค่า) · วัดใน `verify:scale` · จำกัดจำนวนแกนพร้อมกัน |
| SQLite กับ Postgres ต่างกันเงียบ ๆ | ผ่านบนเครื่อง พังบน production | `verify:schema` + รันชุดสำคัญบน Postgres ก่อนทุกหมุด |
| function หมดเวลา | งานค้าง | ก้อนเล็กในคิว · ทำซ้ำได้ |
| AI ตอบผิดรูปหรือเดาผิด | ข้อมูลเพี้ยน | ไม่มีสิทธิ์เขียน · ผลผ่าน schema · เข้า Calibrate ให้คนตัดสิน |

## 12 · นิยาม "เสร็จ"

1. `npm run check` ผ่าน (typecheck + boundaries) — ไม่ใช่ `tsc --noEmit` อย่างเดียว
2. ชุด `verify:*` ที่เกี่ยวข้องผ่าน และชุดใหม่อยู่ใน CI
3. `npm run build` ผ่านใน worktree สะอาด
4. หน้าใหม่ผ่าน axe · ดูได้ที่ความกว้างมือถือ · อยู่ในงบเวลา · ผ่านรีวิวภาพหน้าจอ
5. ข้อความไทย (และอังกฤษตั้งแต่สปรินต์ 9) · วันที่ตามภาษา · ค่าที่ระบบเดามีป้าย
6. ทุกค่าที่ระบบสรุปมีเหตุผล และทุกค่าบนเรคคอร์ดมี Trace
7. การเปลี่ยนจำนวนมากย้อนกลับได้
8. ใช้ได้กับกลุ่มลูกค้าสมมุติอย่างน้อยสองกลุ่มโดยไม่มีเงื่อนไขในโค้ดตามกลุ่ม (ตั้งแต่สปรินต์ 7)
9. ไม่มีข้อมูลจริงของลูกค้าในชุดทดสอบ ภาพหน้าจอ log หรือคำขอที่ส่งให้ AI
