# ส่วน A · ผลิตภัณฑ์

## 1 · ทิศและนิยาม

### 1.1 Multidimensional CRM — นิยามที่เรากำหนด

คำนี้ยังไม่มีความหมายกลาง (เจ้าอื่นใช้หมายถึง "หลายธุรกิจในระบบเดียว" หรือ "วิเคราะห์หลายมุม") เราจึงนิยามเองและพิสูจน์ในเดโม

| | CRM ทั่วไป · มิติเดียว | PARALLAX · หลายมิติ |
|---|---|---|
| หน่วยข้อมูล | คนหนึ่งคน = แถวเดียว | คนหนึ่งคน = จุดตัดของหลายแกน |
| สถานะ | สถานะเดียว (ลีด → ลูกค้า) | บทบาทต่อโปรแกรมต่อช่วงเวลา (ผู้เข้าชม 2017 · ผู้ออกบูธ 2020 · วิทยากร 2024) |
| องค์กร | ช่องข้อความ "บริษัท" | สังกัดที่มีช่วงเวลา — รู้ว่าย้ายงานเมื่อไร ไปไหน |
| คุณภาพข้อมูล | สมมุติว่าสะอาด | ห้ามิติต่อคน + Clarity |
| การแบ่งกลุ่ม | ตัวกรองทีละช่อง | Prism ไขว้แกนใดก็ได้ ทุกช่องคือกลุ่มที่ใช้ได้ทันที |
| ความเหมาะสม | คะแนนลีดก้อนเดียว | คะแนนต่องาน (Focus) |
| ความน่าเชื่อถือ | ค่าล่าสุดที่มีคนพิมพ์ | ทุกค่ามีที่มา กฎที่เลือก และประวัติ (Trace) |

- **แกนโครงสร้าง:** คน × องค์กร × โปรแกรม × บทบาท × เวลา (หัวข้อ 5)
- **แกนคุณภาพ:** ติดต่อได้ไหม · เป็นใคร · เคยทำอะไรกับเรา · อนุญาตอะไรไว้ · เหมาะกับงานไหน (หัวข้อ 6)

### 1.2 กว้างที่ตำแหน่ง แคบที่จุดเจาะ

| | |
|---|---|
| ตำแหน่งในตลาด | Multidimensional CRM สำหรับองค์กร B2B |
| จุดเจาะ | องค์กรที่มีโปรแกรมซ้ำทุกปี — ทุกมิติมีข้อมูลเต็ม จึงเห็นความต่างชัดที่สุด |
| "Corporate" | ข้อมูลแบบ B2B (คนในฐานมาจากองค์กร) — ลูกค้ารายแรกเป็นองค์กรขนาดกลาง ไม่ใช่องค์กรมหาชน |
| ไม่ทำ | ค้าปลีก · POS · ขายรายชื่อ · งานการเมือง |

## 2 · Premium และการขาย

### 2.1 Premium ไม่ใช่ mass market

| เรื่อง | Mass market (ไม่ทำ) | PARALLAX |
|---|---|---|
| ลูกค้า | ใครก็สมัคร | องค์กรที่ผ่าน ICP หลักสิบรายต่อปี |
| การขาย | สมัครเอง · แผนฟรี · บัตรเครดิต | นัดคุย → Database Audit → สัญญารายปี |
| เริ่มใช้ | ลูกค้าย้ายข้อมูลเอง | เราย้ายและล้างให้ · เห็นผลสแกนในสัปดาห์แรก |
| สิ่งที่ขาย | ฟีเจอร์ | ผลลัพธ์: ฐานข้อมูลที่ใช้ได้ + งานที่เป็นรายได้ + ผลที่วัดได้ |
| ผลิตภัณฑ์ | ทำหลายอย่างพอใช้ | ไม่กี่อย่าง แต่ลึกและแม่น |
| ความรู้สึก | เครื่องมือ | ห้องควบคุมข้อมูลขององค์กร — เปิดในห้องประชุมผู้บริหารได้ |
| การดูแล | ศูนย์ช่วยเหลือ | ผู้ดูแลลูกค้า · ทบทวนฐานข้อมูลรายไตรมาส |

### 2.2 เกณฑ์ลูกค้า (ICP) — ต้องผ่าน 3 ใน 4

1. คนในฐาน ≥ 20,000 คน หรือข้อมูลย้อนหลัง ≥ 3 ปี
2. ความสัมพันธ์หนึ่งรายมีมูลค่าสูง (บูธ · สปอนเซอร์ · ค่าสมาชิกองค์กร · หลักสูตร · ดีล B2B)
3. ข้อมูลกระจายหลายทีม/แบรนด์/ระบบ
4. มีคนที่ต้องตอบผู้บริหารว่าฐานข้อมูลสร้างรายได้เท่าไร

ไม่ผ่าน = ไม่รับ แม้อยากจ่าย

### 2.3 โครงการขาย (ตัวเลขเจ้าของกำหนด)

| ขั้น | อะไร | ระบบต้องรองรับ |
|---|---|---|
| 1 นัดคุย | เดโมบนข้อมูลสมมุติ (นัดเท่านั้น ไม่เปิดสาธารณะ) | บัญชีเดโมสองกลุ่ม |
| 2 Database Audit | งาน 2–3 สัปดาห์: ย้ายข้อมูลจริง → สแกน → Golden Record → นำเสนอผู้บริหาร | บัญชีลูกค้า (`is_customer`) · รายงาน Audit |
| 3 สัญญารายปี | ใช้ระบบเต็ม | สถานะการชำระต่อบัญชี (หัวข้อ 10.6) |
| 4 ทบทวนรายไตรมาส | รายงานไตรมาส · เสนองาน Focus ใหม่ | รายงานไตรมาส (C1) |

การจ่าย: ใบเสนอราคา → PO → ใบแจ้งหนี้ · ใบกำกับภาษี · หัก ณ ที่จ่าย 3%
ช่องทาง: เครือข่ายของเจ้าของ (SETA และลูกค้าในมุมอื่น) → แนะนำต่อในวงการ → สมาคมที่ลูกค้าทำงานด้วย · ไม่ซื้อโฆษณาแบบหว่าน

## 3 · คอนเซ็ปต์และภาษาโมดูล

**PARALLAX — The Depth Database for relationship-driven organisations**

parallax คือการมองสิ่งเดียวจากหลายจุดจนเห็นความลึก → ทั้งผลิตภัณฑ์พูดภาษาแสงเดียวกัน
ชื่อโมดูลเป็นอังกฤษ (แบรนด์ ใช้ในห้องประชุมได้ทั้งไทยและต่างชาติ) คำอธิบายบนหน้าจอเป็นไทย

| โมดูล | คืออะไร | ภาษาแสง |
|---|---|---|
| **Sources** | ทุกไฟล์/ระบบที่ส่งข้อมูลเข้า · แม่แบบ · ลำดับความน่าเชื่อถือ | แหล่งแสง |
| **Golden Record** | เรคคอร์ดจริงหนึ่งเดียวของคน/องค์กร | ภาพที่โฟกัสแล้ว |
| **Depth** | ห้ามิติ + ไทม์ไลน์บทบาท บนทุกเรคคอร์ด | ความลึก |
| **Clarity** | ความคมชัดของฐานข้อมูล 0–100 | ความคมชัด |
| **Prism** | ตารางไขว้หลายมิติ | ปริซึมแยกแสง |
| **Lens** | มุมมองที่บันทึกไว้ | เลนส์ |
| **Focus** | งาน: เป้าหมาย + กฎคัด + คะแนน + ปลายทาง | จุดโฟกัส |
| **Calibrate** | ห้องทำงานผู้ดูแลข้อมูล | การปรับเทียบ |
| **Trace** | ที่มาของทุกค่า · ประวัติ · ย้อนเวลา | เส้นทางแสง |
| **Rule Lab** | ทดลองกฎบนสำเนา เห็นผลต่างก่อนใช้ | ห้องทดลอง |
| **Consent Ledger** | สมุดความยินยอมต่อวัตถุประสงค์ แก้ย้อนหลังไม่ได้ | — |
| **Signals** | ผลที่ไหลกลับ (เด้ง · ลงทะเบียน · ดีลได้) | สัญญาณ |
| **Triggers** | อัตโนมัติเมื่อมิติเปลี่ยน | — |
| **Steward** | ผู้ช่วย AI ดูแลข้อมูล (Claude Opus 5.5) — เสนอเท่านั้น | — |

**Relationship Equity** — ตัวเลขผู้บริหาร: มูลค่าโดยประมาณของฐานข้อมูล
= Σ องค์กร (มูลค่าที่เคยเกิด × โอกาสติดต่อได้ × ได้รับอนุญาต) · แสดงตามเวลา · **ป้าย "ประมาณการ" + เปิดวิธีคิดให้ดูเสมอ**
ทำให้งานล้างข้อมูลกลายเป็นตัวเลขที่ผู้บริหารเห็นว่าโตขึ้น

## 5 · แบบจำลองข้อมูล

```
   องค์กร (org) ◀── สังกัด (มีช่วงเวลา) ──▶ คน (person)
       │                                        │
       └──────────▶ การมีส่วนร่วม (participation) ◀┘
```

## 7 · Golden Record (identity resolution)

ระดับเดียวกับ identity resolution ของ Salesforce Data 360 (กฎจับคู่ + กฎเลือกค่า + ลิงก์กลับแหล่ง) แต่อยู่ในตัว

### คีย์ตั้งต้น

| คีย์ | ผล |
|---|---|
| อีเมลส่วนบุคคลตรงกัน | รวมอัตโนมัติ |
| เบอร์มือถือตรงกัน + ชื่อไม่ขัด | รวมอัตโนมัติ |

| อีเมลกลาง (info@ · sales@) | ไม่ใช่คีย์ของคน → ผูกองค์กร |

### การปรับรูป

ชื่อคน: ตัดคำนำหน้า (คุณ · นาย · นาง · นางสาว · ดร. · ผศ. · รศ. · Mr. · Ms. · Dr.) · ช่องว่างไทย · ทับศัพท์หลายแบบ · สลับชื่อ-สกุล ·
องค์กร: ตัด "บริษัท … จำกัด (มหาชน)" · บจก. · Co., Ltd. · PCL · ไทย↔อังกฤษด้วยโดเมน/เลขผู้เสียภาษี · โดเมนอีเมล → องค์กร (ยกเว้นโดเมนฟรี)

### กฎที่ลูกค้าตั้งได้

- **กฎจับคู่** หลายกฎต่อชุด · ฟิลด์ · วิธี (ตรงตัว · ปรับรูป · คล้าย) · เกณฑ์ · ผล (รวมเอง/เข้าคิว)
- **กฎเลือกค่า** ต่อฟิลด์: ล่าสุด · พบบ่อยที่สุด · ลำดับความน่าเชื่อถือของแหล่ง · คนล็อก (ชนะเสมอ)
  เช่น ตำแหน่ง = ล่าสุด · ชื่อบริษัท = แหล่งสัญญาก่อน · เลขผู้เสียภาษี = แหล่งสัญญาเท่านั้น
- ความเข้มเป็นการตัดสินใจทางธุรกิจ → แก้ผ่าน Rule Lab เท่านั้น
- รวมแล้วไม่ลบแถวดิบ · ยกเลิกได้ · **วัดความแม่นทุกครั้งที่แก้กฎ**: precision ≥ 98% · recall ≥ 90% บนข้อมูลที่มีเฉลย

**ระบบทำงานครบโดยไม่มี AI** — ทุกความสามารถมีทางสำรองที่เป็นกฎ (`ai.ts` ทำแบบนี้อยู่แล้ว)

### 11.2 รุ่นและการเรียก

- **ทุกความสามารถใช้ `claude-opus-5-5`** (เจ้าของกำหนด) · effort ต่อความสามารถ: `low` (จัดหมวดสั้น) · `medium` (ค่าตั้งต้นของรุ่นนี้ แต่ตั้งเองทุกครั้ง) · `high` (วิเคราะห์ เขียนยาว)
- thinking ของรุ่นนี้ปิดไม่ได้ — คุมต้นทุนด้วย effort
- ผลที่เครื่องใช้ต่อ → **structured outputs** (`output_config.format`) ทุกครั้ง · ไม่ใช้ forced `tool_choice` (รุ่นนี้ไม่รับ)
- งานที่ไม่มีคนรอ (นำเข้า) → **Message Batches** (ลด 50%) ผ่านคิวงาน · ผลไม่เรียงลำดับ จับด้วย `custom_id`
- **Prompt caching** — ส่วนคงที่ (คำสั่ง · schema · ชุดคำลูกค้า) อยู่หน้า · ตรวจ `cache_read_input_tokens`
- ตรวจ `stop_reason` ก่อนอ่านผลทุกครั้ง · เปิด **server-side fallbacks** (`fallbacks: "default"`) กันการปฏิเสธผิดพลาดกลายเป็นงานล่ม · ถ้ายังปฏิเสธ → ทางสำรอง
- ข้อความยาว (สรุป รายงาน) → streaming
- ตอนนี้ `ai.ts` ใช้ `claude-opus-5` → ย้ายในสปรินต์ 0 (ตรวจแล้ว: เรียก SDK จุดเดียว · structured outputs · effort low · ตรวจ refusal · ไม่ใช้ forced tool_choice หรือปิด thinking → เปลี่ยนชื่อรุ่น + เพิ่ม fallbacks)

### 11.4 AI Gateway — 12 ส่วนที่ต้องมี

```
 ความสามารถ → callSteward(purpose, input)
 ┌──────────────────── lib/engine/ai/ ────────────────────┐
 │ ① Registry   prompt · schema · effort · เวอร์ชัน        │
 │ ② PII guard  ตัดค่าติดต่อก่อนส่ง · สแกนซ้ำ               │
 │ ③ Policy     บัญชีต้อง paid · เปิด/ปิดรายความสามารถ · งบ │
 │ ④ Cache      ai_cache (hash input) + prompt caching    │
 │ ⑤ Call       messages / batches · fallbacks · retry     │
 │ ⑥ Validate   schema ไม่ผ่าน = ทิ้ง · refusal = สำรอง     │
 │ ⑦ Ledger     บัญชี · ความสามารถ · โทเค็น · ค่าใช้จ่าย     │
 └────────────────────────────────────────────────────────┘
 → ป้าย "Claude เสนอ" → Calibrate / ร่าง → คนอนุมัติ → change set (ย้อนได้)
```

1. Gateway จุดเดียว — `boundaries.mts` ห้าม import SDK นอก `lib/engine/ai/`
2. PII guard — ส่งได้: ชื่อ ตำแหน่ง องค์กร โดเมนอีเมล ค่าที่ปิดบาง สถิติรวม · ไม่ส่ง: เบอร์ อีเมลเต็ม LINE ที่อยู่ วันเกิด
3. Registry — prompt/schema/effort/เวอร์ชันเป็นไฟล์ในโค้ด · เปลี่ยน = รัน eval
4. Structured outputs ทุกผลที่เครื่องใช้
5. Human-in-the-loop — ป้าย "Claude เสนอ" ติดถาวรใน Trace
6. **Policy: AI ปิดจนกว่าบัญชีเป็น `paid`** (เจ้าของกำหนด) · บัญชีเดโมสมมุติเปิดได้เพราะไม่มีข้อมูลจริง · ระหว่าง Database Audit ก่อนชำระ ใช้ทางสำรองที่เป็นกฎ
7. Ledger + งบต่อบัญชี — แจ้งเตือน 80% หยุด 100% (ทางสำรองยังทำงาน) · ลูกค้าเห็นในหน้า Audit
8. Batches ผ่าน `work_queue`
9. Prompt caching อย่างตั้งใจ
10. Refusal + fallbacks
11. Evals (11.6)
12. Feedback — บันทึกรับ/แก้/ปฏิเสธ · อัตรารับต่ำกว่า 60% สองสัปดาห์ = ทบทวน · ป้อน A8

| กฎที่ลูกค้าตั้งหลวมเกิน | ผ่าน Rule Lab ก่อน · ชุดใหญ่ต้องอนุมัติ · ย้อนได้ |
| ส่งอีเมลรายชื่อเก่า → โดเมนลูกค้าเสียชื่อ | warm-up บังคับ · หยุดอัตโนมัติ · นำร่องให้ลูกค้าส่งเอง |

| AI ตอบผิดรูป/เดาผิด | ไม่มีสิทธิ์เขียน · schema · Calibrate · eval ก่อนเปิด |

## 29 · ตั้งใจไม่ทำ

- ค้าปลีก · POS · ขาย/ซื้อรายชื่อ · งานการเมืองทุกรูปแบบ
- แผนฟรี · สมัครเอง · ลูกค้าที่ไม่ผ่าน ICP · ปรับแต่งเฉพาะรายที่ใช้กับรายอื่นไม่ได้
- ยิงเช็กอีเมลกับเซิร์ฟเวอร์ผู้รับ
- ระบบลงทะเบียนงาน · ผังบูธ · ขายตั๋วหน้างาน (เชื่อมผ่านนำเข้า/API แทน)
- AppExchange · ภาษาโปรแกรมบนแพลตฟอร์ม · Service · CPQ · territory · marketing automation เต็มรูป · แอปมือถือ (รอบแรก)
- AI ที่รวม แก้ ลบ ส่ง หรือใช้กฎเองโดยไม่มีคน · AI ที่เขียน SQL · AI ที่สร้างตัวเลขข้อเท็จจริง · AI เดาข้อมูลมาตรา 26 · แชตบอตทั่วไป
