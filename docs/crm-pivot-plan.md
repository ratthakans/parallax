# แผนเปลี่ยนทิศ · PARALLAX เป็น CRM แบบ Salesforce

เขียน 2026-10-11 · เพิ่มเรื่อง 100,000 รายชื่อและความเป็น Salesforce วันเดียวกัน · แทนที่ `simplify-plan.md` (แผนนั้นปรับคอนโซลเดิม แผนนี้เปลี่ยนตัวผลิตภัณฑ์)

> แผนก่อนหน้าผมแนะนำว่า *ไม่ทำ pipeline / deal* — เจ้าของตัดสินใจแล้วว่าจะไปทางนี้
> แผนนี้จึงทำตามทิศนั้นเต็มตัว ข้อกังวลที่เหลืออยู่ในหัวข้อความเสี่ยง ไม่ได้ซ่อนไว้

---

## ทิศใหม่ในประโยคเดียว

**CRM ภาษาไทยสำหรับ SME ที่โครงแบบ Salesforce ใช้ง่ายกว่า และทำสิ่งที่ Salesforce ทำไม่ได้:
บอกได้ว่าการติดตามลูกค้าทำให้ขายได้เพิ่มจริงเท่าไร**

Salesforce บอกว่าขายได้เท่าไร — PARALLAX บอกว่า*การกระทำของคุณ*ทำให้ขายได้เพิ่มเท่าไร
เครื่องวัดผลแบบกันกลุ่มไว้ (holdout) ที่สร้างไว้แล้วคือจุดต่าง ไม่ใช่ของที่ต้องทิ้ง

## ห้าเรื่องที่ต้องตัดสินใจก่อนเขียนโค้ด

### D1 · เก็บอีเมลและเบอร์โทรจริง — ✅ ตัดสินใจแล้ว 2026-10-11

> **เจ้าของ: "เก็บ contact ลูกค้าให้เยอะที่สุดเท่าที่ทำได้"** — ทำแล้วในวันเดียวกัน
>
> | | |
> |---|---|
> | ช่องทาง (หลายค่าต่อคน · เข้ารหัส AES-256-GCM) | มือถือ · เบอร์อื่น · อีเมล · LINE · Facebook · Instagram · TikTok · เว็บไซต์ · ที่อยู่ |
> | ประวัติ (อ่านได้ ใช้กรองกลุ่ม) | ชื่อจริง · นามสกุล · ชื่อเล่น · เพศ · วันเกิด · บริษัท · ตำแหน่ง · ตำบล · อำเภอ · จังหวัด · รหัสไปรษณีย์ · หมายเหตุ |
> | ไม่เก็บโดยตั้งใจ | ข้อมูลอ่อนไหว PDPA มาตรา 26 (ศาสนา · เชื้อชาติ · สุขภาพ · ความคิดเห็นทางการเมือง ฯลฯ) · เลขบัตรประชาชน |
> | หน้าจอ | แสดงค่าที่ปิดบางส่วนเสมอ (081-xxx-5678) · ค่าเต็มต้องกดเปิดทีละค่าและถูกบันทึก |
> | นำเข้า | ไฟล์รายชื่อที่ไม่มียอดขายนำเข้าได้แล้ว · จับหัวคอลัมน์ไทย 17 แบบ · นำเข้าซ้ำไม่ซ้ำและไม่ลบของเดิม |
> | ตรวจ | `verify:contacts` 41 ข้อ รวมการค้นไฟล์ฐานข้อมูลทั้งไฟล์ว่าไม่มีค่าจริงหลุด |
>
> **ยังค้าง:** หน้าจอดู/แก้ข้อมูลติดต่อ (ระยะ B) · สิทธิ์ขอส่งออก/ลบข้อมูลรายคนตาม PDPA ·
> ตั้ง `PII_KEY` และ `PII_HMAC_KEY` บน Vercel ก่อน deploy ครั้งถัดไป · กู้โปรเจกต์ Supabase ที่ถูกพักแล้ว apply `0003_contacts.sql`
>
> **การมีเบอร์ไม่ใช่การได้รับอนุญาตให้ส่ง** — การส่งยังผูกกับตาราง `consents` เหมือนเดิมทุกประการ

<details><summary>เหตุผลเดิมก่อนตัดสินใจ</summary>


ตอนนี้ `identities` เก็บ **sha256 อย่างเดียว** CRM ฝั่งขายที่โทรหาใครไม่ได้ไม่ใช่ CRM
ทิศใหม่จึงบังคับให้เก็บค่าจริง — แต่ต้องเก็บแบบนี้:

- เข้ารหัสในฐานข้อมูล (Supabase Vault / pgcrypto) · เก็บ hash ไว้ใช้จับคู่ต่อ
- สิทธิ์ระดับฟิลด์ — ไม่ใช่ทุกคนในทีมต้องเห็นเบอร์
- PDPA: บันทึกวัตถุประสงค์ · ระยะเวลาเก็บ · ส่งออก/ลบตามคำขอ · แจ้งเหตุรั่ว 72 ชม.
- บันทึกว่าใครเปิดดูข้อมูลติดต่อเมื่อไร

### D2 · ขายให้บริษัท (B2B) หรือคนทั่วไป (B2C)

Salesforce ออกแบบมาเพื่อ B2B (บริษัท → ผู้ติดต่อ) แต่ SME ไทยจำนวนมากขายคนทั่วไป
**แนะนำ: บริษัทเป็นช่องที่ไม่บังคับ** — ผู้ติดต่อที่ไม่มีบริษัทคือ "ลูกค้าบุคคล"
(แบบ Person Account ของ Salesforce) โครงเดียวใช้ได้ทั้งสองแบบ

### D3 · โมเดลราคา

ตอนนี้คิดตามจำนวนลูกค้าที่ระบุตัวได้ และเขียนบนหน้าราคาว่า *"Not on seats"*
CRM ที่ทีมขายหลายคนใช้ คิดต่อผู้ใช้สมเหตุสมผลกว่า
**ทางเลือก** — ต่อผู้ใช้ · ตามฐานลูกค้า (แบบเดิม) · ผสม (ผู้ใช้ราคาต่ำ + ขั้นตามฐานลูกค้า)

### D4 · เครื่องวัดผล — เก็บเป็นจุดต่าง (แนะนำ)

ถ้าไม่มีมัน PARALLAX คือ HubSpot ที่ด้อยกว่าและไม่มีแผนฟรี
ถ้ามี มันคือ CRM ตัวเดียวในตลาดไทยที่พิสูจน์ได้ว่าการติดตามทำให้เกิดยอดจริง

### D5 · บัญชีเดโมพรรคการเมือง

ข้อจำกัดเดิมคือบัญชีนี้ทำได้แค่ **บริหารสมาชิกภาพ ห้ามโน้มน้าวผู้มีสิทธิ์เลือกตั้งหรือยิงเป้ารายบุคคล**
pipeline · ลีด · ดีล บนบัญชีพรรค คือเครื่องมือหาเสียงรายบุคคลพอดี
**แนะนำ: ถอดออกจากเดโม CRM** แทนด้วยบัญชีตัวอย่าง B2B สมมุติ (เช่น ตัวแทนจำหน่ายวัสดุ · เอเจนซี)

contacts         ผู้ติดต่อ      = customers เดิม + account_id? · อีเมล* · เบอร์* · LINE* · ตำแหน่ง
                                 · stage (ลีด → สนใจ → ลูกค้า → เสีย) · แหล่งที่มา · owner_id · แท็ก

- **หน้าตาแบบ Salesforce ≠ เอาแบรนด์ Salesforce มา** — ไม่ใช้สีฟ้า Lightning ไม่ใช้ภาพก้อนเมฆ

- ตารางแน่น อ่านเร็ว — ข้อมูลคือพระเอก ไม่ใช่การ์ดใหญ่

## รองรับ 100,000 รายชื่อ

**100,000 แถวเล็กมากสำหรับ Postgres — มันใหญ่เฉพาะกับโค้ดที่ดึงทุกแถวขึ้นมาคิดใน Node**
ซึ่งคือสิ่งที่ระบบทำอยู่ตอนนี้

### วัดจริง

โคลนข้อมูลที่ผ่าน verify ขึ้นเป็น 100,000 คนในฐานแยก แล้วรันเครื่องยนต์ตัวจริง:

| จุด | วัดในเครื่อง (ไม่มีเครือข่าย) | บน production ที่ 100,000 คน |
|---|---|---|
| `loadFeatures` — ถูกเรียกทุกครั้งที่เปิดบรีฟ · คลัง play · ตั้งค่า · กดอนุมัติ | 551 ms · **252 MB** ต่อคำขอ | **76 MB ข้ามเครือข่าย ≈ 50 วินาที** ¹ |
| `runMatch` ทั้งก้อน | 800 ms · 314 MB · กลุ่มใหญ่สุด 65,157 คนเป็น array | + ข้างบน |
| `sendCampaign` — INSERT ทีละคนในธุรกรรมเดียว | 65,157 รอบ | **≈ 1.8 ชั่วโมง** ² ฟังก์ชันถูกตัดก่อนนานมาก |
| นำเข้า — ทั้งไฟล์ผ่าน server action เพดาน `6mb` | — | 100,000 แถว × ~120 ไบต์ ≈ 11 MB **เกินเพดาน** |
| `deriveFeatures` — ดึงลูกค้า + ธุรกรรม + รายการสินค้าทั้งหมดเข้า Node ในปุ่มเดียว | — | ธุรกรรมระดับล้านแถวในคำขอเดียว |
| ค้นหา | ไม่มี | ต้องมี index |
| Supabase แผนฟรี เพดาน 500 MB | ตาราง feature อย่างเดียว 76 MB | รวมธุรกรรม/ข้อความแล้ว **เกิน — ต้องแผน Pro** |

¹ จากที่วัดไว้: payload 1 MB ใช้ 0.86 วินาทีจากโตเกียว · ² RTT ที่วัดได้ 100 ms × 65,157

| **S2** | แปล `selector` ของแต่ละ play เป็น SQL `WHERE` — selector เป็น object ที่ประกาศไว้อยู่แล้ว จึงแปลได้ตรงตัว | นับขนาดกลุ่มในฐาน ไม่ดึงคน 100,000 คนขึ้นมา |
| **S3** | แช่แข็งรายชื่อและส่งด้วย `INSERT … SELECT` ในฐานข้อมูล | 65,157 รอบ → **1 คำสั่ง** |
| **S4** | งานหนักออกจากคำขอ: ตาราง `jobs` + worker (Vercel Cron) สำหรับ derive · นำเข้า · ส่ง · วัดผล พร้อมแถบความคืบหน้า | ไม่มีปุ่มไหนรอนานจนหมดเวลา |
| **S5** | นำเข้า: อัปโหลดตรงไป Supabase Storage (ไม่ผ่านเพดาน 6 MB) · worker อ่านทีละ 5,000 แถว · ตรวจซ้ำด้วย hash ที่มีอยู่แล้ว · upsert | ไฟล์ขนาดไหนก็ได้ นำเข้าซ้ำไม่เกิดรายชื่อซ้ำ |
| **S6** | `deriveFeatures` เขียนใหม่เป็น SQL (window functions) รันกลางคืน | ธุรกรรมล้านแถวไม่ต้องออกจากฐาน |
| **S7** | บรีฟคำนวณไว้ล่วงหน้าแล้วเก็บผล | หน้าแรกอ่านแค่ 3 แถว |
| **S8** | ตาราง UI: แบ่งหน้าแบบ keyset ทีละ 50 แถว · virtual scroll · ค้นหาด้วย `pg_trgm` (หาคำไทยกลางชื่อได้) | เลื่อน 100,000 แถวลื่นเท่า 100 แถว |
| **S9** | Supabase แผน Pro + ย้ายภูมิภาคไปสิงคโปร์ | พื้นที่พอ · RTT จากไทยลดลง |
| **S10** | ด่านใหม่ `verify:scale` seed 100,000 คนแล้วบังคับงบเวลา · กฎ boundary ห้ามเรียก `loadFeatures` บนเส้นทางคำขอ | ไม่ถอยกลับไปช้าโดยไม่มีใครรู้ |

**hash ที่เก็บไว้มีประโยชน์ตรงนี้** — มันคือกุญแจตรวจซ้ำที่พร้อมใช้แล้ว ตอนนำเข้าเบอร์เดียวกันจากสองไฟล์ ระบบรู้ทันทีว่าเป็นคนเดียวกัน

## ใกล้ Salesforce ที่สุด

**Salesforce ไม่ได้เป็น Salesforce เพราะมีลูกค้า บริษัท และดีล — ทุก CRM มีสามอย่างนี้**
มันเป็น Salesforce เพราะสองอย่าง:

1. **แอดมินปรับ CRM ให้เข้ากับธุรกิจได้เองโดยไม่ต้องเขียนโค้ด**
2. **ข้อมูลยังน่าเชื่อถือแม้มีเป็นล้านแถวและคนใช้เป็นร้อย** — สิทธิ์ · ประวัติการแก้ไข · การตรวจซ้ำ

เรียงตามความเป็น Salesforce มากไปน้อย พร้อมเวอร์ชันที่ SME ใช้ได้จริง:

| | ของ Salesforce | เวอร์ชัน PARALLAX |
|---|---|---|
| **1** | **Object Manager** — ฟิลด์กำหนดเอง | ชนิด ข้อความ · ตัวเลข · เงิน · วันที่ · ตัวเลือก · ใช่/ไม่ — เพิ่มแล้วโผล่เองในหน้าเรคคอร์ด · list view · ตัวกรอง · การนำเข้า · รายงาน ไม่ต้องแก้โค้ด |
| **2** | **List view** | เลือกคอลัมน์ · กรองทุกฟิลด์ · บันทึกและแชร์มุมมอง · แก้ในตาราง · **ทำทีละหลายแถว** (เปลี่ยนเจ้าของ · เปลี่ยนขั้น · ใส่แท็ก · เพิ่มเข้าแคมเปญ · ลบ) |
| **3** | **Profiles · Roles · Sharing** | สามบทบาท เจ้าของ / ผู้จัดการ / พนักงานขาย · เลือกได้ว่า "เห็นทั้งทีม" หรือ "เห็นเฉพาะของตัวเอง หัวหน้าเห็นของลูกทีม" · ซ่อนเบอร์โทรตามบทบาท — **บังคับที่ RLS** ซึ่งต่อไว้แล้ว |
| **4** | **Data quality** | ตรวจรายชื่อซ้ำ (เบอร์ · อีเมล · ชื่อ) · รวมเรคคอร์ด · ประวัติการแก้ทุกฟิลด์ · ถังขยะ 30 วัน · ฟิลด์บังคับกรอก |
| **5** | **Lead management** | ฟอร์มรับลีดจากเว็บและ LINE · แจกลีดอัตโนมัติแบบวนคน · คะแนนลีดจากเครื่องยนต์เดิม · แปลงลีดเป็นผู้ติดต่อ + บริษัท + ดีลในคลิกเดียว |
| **6** | **Opportunity** | ขั้นพร้อมโอกาสปิด % · สินค้าในดีล (รายการ + ราคา) · เหตุผลที่ได้/เสีย · คาดการณ์ยอดรายเดือน |
| **7** | **Reports & Dashboards** | สร้างรายงานเอง: เลือกเรคคอร์ด → กรอง → จัดกลุ่ม → นับ/รวม → กราฟ · แดชบอร์ดลากวาง |
| **8** | **Flow** (อัตโนมัติ) | "เมื่อ … ถ้า … ให้ …" เช่น ดีลเข้าขั้นเสนอราคา → สร้างงานโทรตามใน 2 วัน · ลูกค้าเลยรอบ → ส่ง LINE · **play เดิม 23 ตัวกลายเป็นสูตรสำเร็จรูปของตัวนี้** |
| **9** | **Chatter** | คอมเมนต์และ @แท็กเพื่อนบนเรคคอร์ด · ติดตามเรคคอร์ด · แจ้งเตือน |
| **10** | **API** | REST ทุกเรคคอร์ด · webhook เมื่อข้อมูลเปลี่ยน · ส่งออกข้อมูลทั้งหมดได้ทุกเมื่อ |
| **11** | **Security** | ยืนยันตัวตนสองชั้น · บันทึกว่าใครเปิด/แก้อะไรเมื่อไร |
| **12** | **Einstein** | **มีแล้ว** — ความเสี่ยงหาย · วันซื้อครั้งถัดไป · วิธีที่แนะนำ + **การวัดผลแบบกันกลุ่ม ซึ่ง Einstein ไม่มี** |

### สิ่งที่ Salesforce ทำได้ไม่ดีในไทย — และเป็นที่ที่ PARALLAX ชนะได้

LINE OA สองทาง (ส่งและรับในไทม์ไลน์) · เบอร์ไทยจัดรูปแบบอัตโนมัติ · ที่อยู่ไทย จังหวัด/อำเภอ/ตำบล/รหัสไปรษณีย์ ·
ค้นหาคำไทยได้จริง · แสดงปี พ.ศ. · ภาษาไทยทุกหน้าจอ · ราคาที่ SME ไทยจ่ายไหว

### สิ่งที่ตั้งใจไม่ลอก

Custom object · การเขียนโค้ดบนแพลตฟอร์ม (Apex) · sandbox · territory · CPQ · Service Cloud · AppExchange

ทั้งหมดคือเหตุผลที่บริษัทต้องจ้างที่ปรึกษา Salesforce มาตั้งค่าให้ — **เราลอกความสามารถ ไม่ลอกความซับซ้อน**

### 6 · ดีล

## ความเสี่ยง

- **ไปแข่งตรงกับ Salesforce · HubSpot · Zoho** ซึ่งมีแผนฟรี — ต้องชนะด้วยสามอย่างที่เขาไม่มีพร้อมกัน:
  **ไทยทั้งระบบ · LINE เป็นช่องทางหลัก · วัดผลได้จริง** ขาดข้อใดข้อหนึ่งคือ HubSpot ที่แย่กว่า
- **เก็บ PII จริง = ภาระตาม PDPA** ที่ระบบตอนนี้หลีกเลี่ยงได้โดยการออกแบบ — ถอยกลับยาก
- **ข้อความทั้งเว็บต้องเขียนใหม่** — ทุกหน้าตอนนี้ขายเรื่อง "ต้นทุนต่อลูกค้าที่กลับมา" และ "สามงานต่อวัน"
