เก็บ **ตัวตน · องค์กร · ความสัมพันธ์ · ความสนใจและความต้องการ · ปฏิสัมพันธ์ · โอกาส · เงื่อนไขใช้ข้อมูล · เวลา** เท่าที่มีหลักฐาน
- ช่องที่ไม่ทราบแสดงว่า "ไม่ทราบ" — **ไม่เติมด้วยคะแนนหรือการเดา**
- ความสัมพันธ์แสดงเป็นรายการในแฟ้มบริษัท + ประวัติตามเวลา
- แผนที่กราฟเต็ม · หาเส้นทางแนะนำหลายทอด · ค้นด้วยภาษาธรรมชาติ = ระยะขยายเมื่อพิสูจน์ประโยชน์

### 3.3 งานประจำสัปดาห์ที่ระบบต้องรองรับ

| ใคร | เมื่อไร | ทำอะไรในระบบ |
|---|---|---|
| BD | ก่อนพบลูกค้า | เปิดแฟ้มบริษัท + brief |
| BD | หลังพบลูกค้า | บันทึกผลและขั้นตอนถัดไป (ปฏิสัมพันธ์ + งาน) |
| หัวหน้าทีม | ทุกสัปดาห์ | ทบทวนบัญชีเป้าหมาย งานค้าง โอกาสที่คืบหน้า (หน้าทบทวนรายสัปดาห์) |
| Data steward | ทุกสัปดาห์ | ตรวจข้อมูลใหม่ ข้อมูลขัดแย้ง รายการที่ต้องยืนยัน (คิว Data Vault) |

**วัดการใช้งานจากกิจกรรมที่มีผล** (มอบหมาย · อัปเดตผล · ทบทวนบัญชี) แยกจากการ login · การกระทำของทีม PARALLAX (ธง `is_staff`) ไม่นับ

### 3.4 เลื่อนออกไป

CRM ทุกแผนก · forecast ซับซ้อน · automation builder · marketplace รายชื่อ · ส่งการตลาดอัตโนมัติหลายช่องทาง · ซิงก์ Salesforce สองทาง ·
ใน pilot ใช้ช่องทางที่ลูกค้าอนุมัติ เก็บผลกลับโดยมีเจ้าของงาน · ไม่เปิดเผยข้อมูลผ่านเครื่องมือที่ยังไม่ผ่านการประเมิน

### 3.5 เกณฑ์เดโม (แทน "เกณฑ์ 30 วินาที" ของฉบับ 5) — ทดสอบอัตโนมัติด้วย `verify:demo`

1. **แฟ้มบริษัทตามเวลา** — คนในบริษัท บทบาท ช่วงเวลา และความสัมพันธ์ที่ยืนยันพร้อมผู้ยืนยัน · ช่องที่ไม่ทราบแสดงว่าไม่ทราบ
2. **หลักฐานทุกค่า** — กดค่าใดก็ได้ เห็นแหล่ง (ไฟล์ แถว) เวลาที่บันทึก เวลาตรวจล่าสุด และประวัติรุ่น
3. **สถานะใช้ข้อมูลพร้อมเหตุผล** — คนเดียวกัน Eligible สำหรับวัตถุประสงค์หนึ่ง และ Suppressed/Review required สำหรับอีกวัตถุประสงค์ พร้อมรุ่นนโยบาย
4. **วงจรแคมเปญ** — เกณฑ์ → รายชื่อเป้าหมายพร้อมเหตุผล → มอบหมาย → บันทึกผล → หน้าทบทวนรายสัปดาห์

## 4 · โครงสร้างข้อมูล (Blueprint บท 3)

### 4.1 กลุ่มข้อมูล → ตาราง

เวอร์ชันแรกใช้เฉพาะส่วนที่หนึ่งแคมเปญต้องใช้ แต่หลักฐานและเงื่อนไขใช้ข้อมูลต้องครบ

| กลุ่มใน Blueprint | ตาราง | หมายเหตุ |
|---|---|---|
| Person และ Contact Point | `customers` (คงชื่อ) · `contact_points` (+ `verify_status` · `valid_from/valid_to` · `last_verified_at`) | เข้ารหัส AES-GCM + HMAC (มีแล้ว) |
| Organization และ Affiliation | `orgs` (+ `parent_id` · `tax_id` · `branch_code` · `legal_entity` แยกบริษัทในเครือ) · `affiliations` (คน · องค์กร · บทบาท · `valid_from/valid_to`) | |
| Relationship Assertion | `relationship_assertions` (ต้นทาง · ปลายทาง · ประเภท · บริบท · หลักฐาน · ผู้ยืนยัน · `valid_from/valid_to`) | ใหม่ — คน↔คน · คน↔องค์กร · องค์กร↔องค์กร |
| Interaction และ Participation | `interactions` (ประชุม · โทร · อีเมลนอกระบบ · ผล · ผู้รับผิดชอบ) · `participations` (ร่วมงาน/กิจกรรม · บทบาท) | |
| Opportunity และ Task | `opportunities` (ข้อเสนอ · บริษัท · ผู้เกี่ยวข้อง · ขั้น · เจ้าของ) · `tasks` (งานถัดไป · กำหนด · เจ้าของ · ผล) | |
| Source และ Import Batch | `sources` (แหล่ง · วัตถุประสงค์ · เจ้าของ · ขอบเขตสิทธิ · ฟิลด์ที่เลือก) · `import_batches` · `import_rows` (ผลรายแถว: สำเร็จ · ปฏิเสธ · รอตรวจ · พักใช้ + เหตุผล) · `source_rows` (ค่าดั้งเดิมเข้ารหัส) | |
| Purpose และ Processing Record | `purposes` · `processing_records` (ฐาน · ขอบเขตข้อมูล · ผู้อนุมัตินโยบาย · รุ่น) — เชื่อมทะเบียนกิจกรรม (ROPA) | ใหม่ |
| Preference และ Evidence | `preferences` (ความยินยอม · ถอน · คัดค้าน · ข้อจำกัด ต่อวัตถุประสงค์/ช่องทาง) · `evidence` (หลักฐานแนบ) — **เพิ่มอย่างเดียว** | แทน `consents` ก้อนเดียว (คงไว้เป็น view สถานะล่าสุด) |

### 4.2 ข้อมูลกำกับบนทุกระเบียน

`tenant_id` · รหัสภายในถาวร · `classification` (สาธารณะ · ภายใน · ลับ · จำกัดสูง) · `data_owner_id` · `source_id` · `recorded_at` · `last_verified_at` ·
`retention_rule_id` · `restriction_status` · `lifecycle_state` + `state_owner_id` + `state_due_at` · ระดับฟิลด์: หลักฐานและสถานะยืนยันเมื่อจำเป็น

ระดับความลับคุมการปิดบังฟิลด์และการส่งออก · ข้อมูลสาธารณะที่ระบุตัวบุคคลได้ยังต้องตรวจเงื่อนไข

### 4.3 สองเวลาและการเก็บรุ่น

- **เวลาที่เป็นจริง** (`valid_from/valid_to`: เมื่อคนนี้อยู่บริษัทนี้จริง) และ **เวลาที่ระบบรับรู้** (`recorded_at` + รุ่นใน `record_versions`)
- ตอบได้ว่า "ณ วันที่ตัดสินใจ ทีมเห็นข้อมูลชุดใด" · ไม่เขียนทับข้อเท็จจริงเดิม · บันทึกผู้เปลี่ยน

### 4.4 กติกาการระบุตัวตน

| สัญญาณ | ผล |
|---|---|
| อีเมลส่วนบุคคลตรงกัน + ชื่อเข้ากันได้ + ไม่ใช่อีเมลกลาง | รวมเองได้ (ความมั่นใจสูง) — ยังแสดงผลกระทบและย้อนได้ |
| อีเมลบริษัทตรงกันแต่ชื่อต่าง | **รอตรวจ** (อีเมลอาจถูกนำไปใช้ใหม่) |
| ชื่อเหมือน · โดเมนเดียวกัน · ร่วมงานเดียวกัน | **สัญญาณให้ตรวจ — ไม่รวมเอง** |
| อีเมลกลาง (info@ · sales@) | ไม่ใช่คีย์ของคน → ผูกองค์กร |
| บริษัทในเครือ | **ไม่รวมเป็นนิติบุคคลเดียว** — เชื่อมด้วย `parent_id` |

- เก็บค่าดั้งเดิมคู่ค่าปรับรูป · ชื่อไทย/อังกฤษ · เบอร์ต่างประเทศ (E.164) · ชื่อย่อบริษัท
- **ก่อนรวมแสดงผลกระทบ** ต่อดีล ความสัมพันธ์ สิทธิ์ และข้อจำกัดการติดต่อ · **ใช้ข้อจำกัดที่เข้มกว่าไว้ก่อนจนตรวจแล้ว**
- ย้อน merge ได้โดยไม่ทำให้ประวัติการติดต่อหาย

## 5 · การนำเข้าและวงจรคุณภาพ (Blueprint บท 4)

### 5.1 ขั้นตอนรับข้อมูล → งานในระบบ

| ขั้น Blueprint | สิ่งที่ระบบทำ |
|---|---|
| 1 ลงทะเบียนแหล่ง | ฟอร์ม `sources`: วัตถุประสงค์ · เจ้าของงาน · ขอบเขตสิทธิ · **เลือกเฉพาะฟิลด์ที่จำเป็น** · ไม่มีแหล่งที่ลงทะเบียน = อัปโหลดไม่ได้ |
| 2 อัปโหลดปลอดภัย | signed URL ไป Supabase Storage (เข้ารหัสระหว่างทาง) · ตรวจชนิด/ขนาด · **สแกนมัลแวร์ก่อนแตะไฟล์** (ไฟล์อยู่ในพื้นที่กักจนผ่าน) · แยกวิเคราะห์ในงานเบื้องหลัง · อ่าน xlsx แบบอ่านค่าอย่างเดียว ไม่รัน macro/สูตร |
| 3 ตัวอย่างและยืนยัน | ตัวอย่างการจับคู่คอลัมน์ การแปลงรูปแบบ (และผลอ่านนามบัตรเมื่ออยู่ในขอบเขต) · **ผู้ใช้ยืนยันก่อนบันทึกข้อมูลหลัก** |
| 4 ตรวจซ้ำและขัดแย้ง | เหตุผล + ความมั่นใจ · รายการเสี่ยงเข้าคิวคนตรวจ · นำเข้าซ้ำไม่สร้างสำเนา (hash ไฟล์ + รหัสต้นทาง) |
| 5 ผลรายแถว | `import_rows` พร้อมรหัสต้นทาง: สำเร็จ · ปฏิเสธ · รอตรวจ · พักใช้ · **รายงานตรวจยอด** (รายการเข้า = รายการออกทุกสถานะ) |

OCR และ AI ภายนอก: ผ่านการประเมินผู้ให้บริการและเส้นทางข้อมูลก่อน · ไม่ส่งภาพนามบัตรหรือทั้งไฟล์ให้บริการที่ยังไม่อนุมัติ

### 5.2 สถานะตลอดอายุข้อมูล

`received → pending_review → confirmed → needs_review → restricted → deleted | anonymised`
- ทุกสถานะมีเจ้าของและวันครบกำหนด · **รายการรอตรวจเกินกำหนดถูกแจ้งเตือน และหมดอายุตามนโยบาย** ไม่ค้างไม่มีกำหนด
- ข้อมูลที่ยืนยันแล้วกลับไปรอตรวจได้เมื่อ: หลักฐานขัดแย้ง · เปลี่ยนงาน · ขาดการยืนยันตามนโยบาย
- อายุข้อมูลตั้งต่อประเภท ไม่ใช้ค่าเดียวทุกประเภท

### 5.3 ตัวชี้วัดคุณภาพ (แทน Clarity score)

รายการต้นทาง · คนและบริษัทที่ยืนยันแล้ว · สัดส่วนที่ทราบแหล่ง · ซ้ำที่รอตรวจ · ข้อมูลเก่า · รายการที่เงื่อนไขการใช้ครบ
**แยกตัวเลขจริงออกจากประมาณการ** · ไม่ใช้คะแนนรวมก้อนเดียวในเวอร์ชันแรก

**ความแม่นยำการรวมตัวตน** วัดกับชุดตัวอย่างที่คนตรวจ — รายงานทั้งรวมผิด (precision) และพลาดซ้ำ (recall)
- ระบบมีเครื่องมือสุ่มตัวอย่างให้ data steward ตรวจ (สุ่มจริง ไม่เลือกเฉพาะผลดี)
- ข้อมูลสมมุติพร้อมเฉลยใช้ทดสอบก่อนมีข้อมูลจริง — **ไม่ใช่หลักฐานความแม่นยำบนข้อมูลลูกค้า**
- ความมั่นใจของโมเดลไม่ใช่ค่าความแม่นยำ

## 6 · กติกาการใช้ข้อมูลและการติดต่อ (Blueprint บท 5)

### 6.1 บริการนโยบาย (`lib/engine/policy/`)

ผลตัดสินต่อ **วัตถุประสงค์ × ช่องทาง × ข้อความ × เวลา** — ไม่ใช้ช่อง consent เดียวครอบทุกกรณี

| สถานะ | พฤติกรรม |
|---|---|
| **Eligible** | ผ่านนโยบายสำหรับงานที่ระบุ · แนบหลักฐานและรุ่นนโยบาย |
| **Review required** | หลักฐานไม่พอ → ต้องตรวจก่อนสร้างการติดต่อ · **Unknown ถูกพัก** |
| **Suppressed** | คัดค้าน · ถอนในขอบเขตนั้น · ข้อจำกัดที่เกี่ยวข้อง |
| **Channel invalid** | ช่องทางใช้ไม่ได้/ส่งไม่สำเร็จ — ไม่ใช่ข้อสรุปฐานทางกฎหมาย |

### 6.2 การบังคับใช้

- ก่อนส่งข้อความหรือส่งรายชื่อเพื่อแคมเปญ ตรวจ: องค์กรลูกค้า · สิทธิ์ผู้ใช้ · วัตถุประสงค์ · ฐานและหลักฐาน · ขอบเขตช่องทาง · คัดค้าน · ถอน · อายุข้อมูล · ข้อจำกัดการเปิดเผย
- **บริการนโยบายใช้ไม่ได้ = หยุดงาน** (fail closed)
- **ตรวจอีกครั้งก่อนส่งจริง** ไม่อาศัยสถานะตอนสร้างกลุ่ม · ถอน/คัดค้าน → ยกเลิกงานที่ยังไม่ส่ง และกระจายไป connector
- เก็บเหตุผลการตัดสินและรุ่นนโยบาย **โดยไม่คัดลอกข้อมูลส่วนบุคคลลง log**
- ครอบคลุม หน้าจอ · API · งานเบื้องหลัง · AI · การส่งออกเพื่อการตลาด · การส่งออกเพื่อคำขอสิทธิ/ย้ายระบบ/หน้าที่ตามกฎหมาย ใช้กระบวนการเฉพาะ

### 6.3 กรณีที่ต้องแยก (ทดสอบใน `verify:policy`)

- ซื้อบัตร → ข้อความบริการได้ ≠ ข้อเสนอทุกประเภท
- ยินยอมรับข่าวจากผู้จัดงาน ≠ อนุญาตส่งข้อมูลให้สปอนเซอร์ · การเปิดเผยต่อบุคคลอื่นตรวจแยก
- ถอนความยินยอมมีผลในขอบเขตที่อาศัยความยินยอมนั้น · คัดค้าน direct marketing ต้องหยุดใช้เพื่อการตลาด
- **ห้ามเปลี่ยนฐานอัตโนมัติเพื่อหลบการถอน/คัดค้าน** · **ไม่ส่งแคมเปญขอความยินยอมใหม่ให้กลุ่มไม่ทราบสถานะโดยอัตโนมัติ**

## 7 · PDPA คำขอสิทธิ อายุข้อมูล เหตุละเมิด (Blueprint บท 6–7)

### 7.1 บทบาท

ลูกค้า corporate = ผู้ควบคุมข้อมูล · PARALLAX = ผู้ประมวลผลตามคำสั่ง (ยืนยันตามกิจกรรมจริง)
PARALLAX เป็นผู้ควบคุมแยกสำหรับ บัญชีผู้ใช้ · การเรียกเก็บเงิน · ความปลอดภัยของบริการ → มีประกาศและฐานของตนเอง

### 7.2 สิ่งที่ต้องมีก่อนใช้ข้อมูลจริง

| รายการ | ในระบบ | เอกสาร |
|---|---|---|
| ทะเบียนกิจกรรมการประมวลผล (ROPA) | `processing_records` เชื่อมกับนโยบายที่ระบบบังคับใช้ · ส่งออกได้ | ✅ |
| Privacy notice ตามกิจกรรม | `notices` เก็บรุ่น ภาษา เวลา วิธีแจ้ง · **แยกการรับทราบประกาศออกจากการให้ความยินยอม** | ✅ |
| การประเมิน legitimate interests | ช่องแนบผลประเมินต่อวัตถุประสงค์ · ไม่ตั้งค่าว่า B2B ใช้ฐานนี้ได้ทุกกรณี | ✅ |
| ข้อมูลจากแหล่งอื่น/ข้อมูลเก่า | ลงทะเบียนแหล่งต้องระบุเงื่อนไขการได้มาและการแจ้ง · นามบัตร/ข้อมูลสาธารณะไม่ใช่ใช้ได้ทุกวัตถุประสงค์ | ✅ |
| DPA | — | คำสั่ง · ความลับ · security · ผู้ให้บริการช่วง · เหตุละเมิด · คำขอสิทธิ · การตรวจสอบ · คืน/ลบเมื่อสิ้นสัญญา |
| ข้อมูลอ่อนไหว (มาตรา 26) | ตัวนำเข้าตรวจและแยกคอลัมน์เสี่ยง (เช่น สุขภาพจากแบบฟอร์มกิจกรรม) · กฎและสิทธิ์แยก · AI ไม่อนุมาน | ✅ |

การยืนยันความสอดคล้อง PDPA ทำโดยผู้รับผิดชอบกฎหมายหรือ DPO ก่อนเปิดบริการ — แผนนี้ช่วยออกแบบให้รองรับ ไม่ใช่การรับรอง

### 7.3 ผู้ให้บริการช่วงและที่ตั้งข้อมูล (ร่างทะเบียน)

| ผู้ให้บริการ | ใช้ทำอะไร | ที่ตั้ง/ภูมิภาค | ต้องตรวจ |
|---|---|---|---|
| Supabase | ฐานข้อมูล · Auth · Storage | โตเกียว | การเก็บรักษา · backup · การเข้าถึงของ support |
| Vercel | เว็บและ function | function ที่ `hnd1` (โตเกียว) · CDN ทั่วโลก | log · ภูมิภาคที่เก็บ log |
| Anthropic (Claude Opus 5.5) | AI brief และงาน AI อื่นเมื่อเปิด | ประมวลผล `us`/`global` (ไม่มีตัวเลือกเอเชีย) | เงื่อนไขเก็บ prompt/output · ไม่ใช้ข้อมูลลูกค้าฝึกโมเดล · ZDR ต้องตกลงแยก |
| บริการสแกนมัลแวร์ (T4) | สแกนไฟล์ก่อนเปิด | ตามตัวเลือก | ห้ามส่งไฟล์ลูกค้าไปบริการสแกนสาธารณะ |
| OCR นามบัตร (เมื่ออยู่ในขอบเขต) | อ่านนามบัตร | ตามตัวเลือก | ประเมินก่อนใช้ |
| monitoring · backup · support | ตามที่เลือก | — | บันทึกประเทศและการเข้าถึง |

**การเก็บฐานหลักในไทยเป็นตัวเลือกผลิตภัณฑ์ ไม่ใช่ข้อสรุปว่าสอดคล้อง PDPA** — Supabase ไม่มีภูมิภาคไทย ถ้าลูกค้าต้องการต้องเปลี่ยนโครงสร้าง (ระยะ E)
การใช้ AI = การโอนข้อมูลออกนอกประเทศ (มาตรา 28/29) → ระบุใน DPA · ส่งเท่าที่จำเป็น · ลูกค้าปิด AI ได้

### 7.4 คำขอสิทธิ (DSAR)

- ช่องทางรับที่ค้นง่าย · ยืนยันตัวตนเท่าที่จำเป็น · จัดประเภท · กำหนดเจ้าของเรื่อง
- ค้นใน ฐานหลัก · เอกสาร · ความสัมพันธ์ · connector · **ข้อมูลที่ AI สร้าง** · ตรวจข้อมูลของบุคคลอื่นก่อนเปิดเผย
- รองรับ เข้าถึง · แก้ไข · โอน · คัดค้าน · ถอน · ลบ · จำกัดการใช้ · กรอบเวลาตามประเภท — **คำขอเข้าถึงไม่เกิน 30 วัน** (ตัวนับเวลาในระบบ)
- บันทึกการดำเนินการหรือเหตุปฏิเสธ

### 7.5 อายุข้อมูล

ก่อนนำเข้าจริง ลูกค้ายืนยันกฎแยกสำหรับ: ไฟล์ต้นทาง · ภาพนามบัตร · ข้อมูลติดต่อ · ประวัติกิจกรรม · หลักฐานความยินยอม · log · ข้อมูล AI · backup
- แต่ละกฎมี เหตุเริ่มนับ · ระยะเวลา · การทบทวน · ผู้รับผิดชอบ · ข้อยกเว้น legal hold
- **ไม่มีตัวเลือก "เก็บตลอดไป" เป็นค่าเริ่มต้น**
- เก็บข้อมูลขั้นต่ำเพื่อรักษาข้อจำกัดการติดต่อ (เช่น HMAC ของช่องทางที่ถูก suppress) — ข้อมูลแฮชยังเป็นข้อมูลส่วนบุคคล
- **การลบตามไปถึง** search index · cache · สรุป AI (`ai_cache`) · ผู้รับข้อมูลตามข้อตกลง · backup มีรอบหมดอายุที่เปิดเผย
- **ทะเบียนการลบ** (`deletion_registry`) ถูกใช้ซ้ำหลังกู้คืน backup ก่อนเปิดบริการ — ข้อมูลที่ลบไม่กลับมา

### 7.6 เหตุละเมิด

ทีม security รับแจ้ง → กักเหตุ → เก็บหลักฐาน → ระบุขอบเขต → **แจ้งผู้ควบคุมข้อมูลเบื้องต้นภายใน 24 ชม.** (ข้อเสนอเชิงสัญญา) ·
ผู้ควบคุมประเมินและแจ้งสำนักงานภายใน 72 ชม. เท่าที่ทำได้ · แจ้งเจ้าของข้อมูลเมื่อเสี่ยงสูง · บันทึกเวลา เหตุผล ข้อมูลที่ยังไม่ครบ ·
**ซ้อมเหตุก่อนเปิดบริการ** (คู่มือ `docs/runbooks/incident.md`)

### 9.1 เส้นทางข้อมูล

```
แหล่งที่อนุมัติ (sources)
```

### 9.2 AI ในระยะแรก — Claude Opus 5.5 ผ่าน AI gateway

| | เวอร์ชันแรก (ระยะ B–C) | เมื่อไรจึงเพิ่ม |
|---|---|---|
| **สรุปแฟ้มบริษัทพร้อมแหล่งอ้างอิง** | ✅ หลังข้อมูลผ่านการตรวจ · ทุกประโยคชี้หลักฐาน (citations) · ช่องที่ไม่มีหลักฐานบอกว่าไม่ทราบ | — |
| เดาหัวคอลัมน์ตอนนำเข้า | ✅ ส่งเฉพาะชื่อหัวคอลัมน์ ไม่ส่งค่าในแถว · ผู้ใช้ยืนยัน | — |
| AI ช่วยจับคู่ตัวตน | ❌ เริ่มด้วยกฎ + คิวคนยืนยัน | เมื่อมีชุดทดสอบความแม่นยำที่คนตรวจ และพิสูจน์ว่าเพิ่ม recall โดย precision ไม่ลด |
| แปลงตำแหน่ง/จัดหมวดอุตสาหกรรม | ❌ ใช้พจนานุกรม + คนยืนยัน | ระยะ D ถ้าข้อมูลการใช้งานบอกว่าจำเป็น |
| ค้นด้วยภาษาธรรมชาติ · ร่างแผน BD หลายขั้น | ❌ | ระยะ E |
| OCR นามบัตร | ❌ (ขอบเขตแยก) | เมื่อลูกค้าซื้อขอบเขต + ผ่านประเมินผู้ให้บริการ (ตัวเลือก: Claude vision ผ่าน gateway เดียวกัน) |

**AI ไม่มีอำนาจ:** ตัดสินฐานกฎหมาย · สร้างความยินยอม · รวมตัวตนเสี่ยงสูง · ส่งข้อความภายนอกโดยลำพัง

**กติกา gateway (`lib/engine/ai/`)**
1. `boundaries.mts` ห้าม import `@anthropic-ai/sdk` นอก gateway
2. **กรองสิทธิ์ก่อนส่งข้อมูลเข้าโมเดล** · ตรวจสิทธิ์ปัจจุบันอีกครั้งก่อนแสดงคำตอบ แหล่งอ้างอิง และสรุปที่เก็บไว้ · **เปลี่ยนสิทธิ์ = ล้าง cache ที่เกี่ยวข้อง**
3. ส่งเท่าที่จำเป็น — ไม่ส่งค่าช่องทางติดต่อจริง · ระดับ "จำกัดสูง" ไม่ส่งเลย
4. บันทึก (`ai_ledger`): ผู้ให้บริการ · รุ่นโมเดล · หลักฐานที่ใช้ · โทเค็น · ค่าใช้จ่าย · ตามนโยบายการเก็บ prompt/output
5. ไม่ใช้ข้อมูลลูกค้าฝึกโมเดลหรือผสมข้าม tenant — **ยืนยันเงื่อนไขกับ Anthropic** (O4)
6. เอกสาร/อีเมล/ไฟล์ = **ข้อมูลไม่น่าเชื่อถือ** · AI ไม่มีเครื่องมือที่เขียนข้อมูลหรือส่งออก · ทดสอบ prompt injection การรั่วไหล และคำตอบไม่มีหลักฐานก่อนเปิด
7. **สวิตช์ปิด AI** ต่อบัญชีและทั้งระบบ — งาน CRM หลักทำต่อได้
8. **AI ปิดจนกว่าบัญชีชำระเงิน** (`billing_state = paid`) — เจ้าของกำหนด · pilot เป็น paid pilot จึงเปิดได้เมื่อชำระค่า pilot
9. รุ่น `claude-opus-5-5` · structured outputs สำหรับผลที่เครื่องใช้ต่อ · ตรวจ `stop_reason` ก่อนอ่านผล · server-side fallbacks เปิดไว้ · effort ตั้งเองต่อความสามารถ (brief = `high`, หัวคอลัมน์ = `low`)

ตอนนี้ `ai.ts` ใช้ `claude-opus-5` → ย้ายเป็น `claude-opus-5-5` ในงาน B1 (ตรวจแล้ว: เรียก SDK จุดเดียว · structured outputs · ตรวจ refusal · ไม่ใช้ forced tool_choice หรือปิด thinking)

### 14.3 การตัดสินใจของ founder

- ลงทุนขยายเมื่อ paid pilot เสร็จ ≥ 3 ราย และ ≥ 2 รายจ่าย subscription ต่อด้วย workflow หลักที่ใช้ซ้ำได้
