# Runbook · เหตุละเมิดข้อมูลส่วนบุคคล

ใช้เมื่อ: สงสัยว่าข้อมูลรั่ว/ถูกเข้าถึงโดยไม่มีสิทธิ์/สูญหาย — **สงสัยก็เริ่มนับเวลา** ไม่ต้องรอยืนยัน
บทบาท (plan 7.1): ลูกค้าเป็นผู้ควบคุมข้อมูล · PARALLAX เป็นผู้ประมวลผล → เราแจ้งลูกค้า ลูกค้าแจ้งสำนักงาน

## เส้นเวลา

| เมื่อ | ทำ |
|---|---|
| 0 | เปิดเหตุ: จดเวลาที่รู้ · ใครแจ้ง · อาการ · ตั้งผู้รับผิดชอบ |
| ≤ 1 ชม. | กักเหตุ (ด้านล่าง) · เก็บหลักฐานก่อนแก้อะไร |
| **≤ 24 ชม.** | **แจ้งผู้ควบคุมข้อมูล (ลูกค้า) เบื้องต้น** — สิ่งที่รู้ · สิ่งที่ยังไม่รู้ · สิ่งที่ทำไปแล้ว (ข้อเสนอเชิงสัญญา) |
| ≤ 72 ชม. | ผู้ควบคุมประเมินและแจ้งสำนักงาน PDPC เท่าที่ทำได้ — เราส่งข้อมูลประกอบ |
| ตามความเสี่ยง | ผู้ควบคุมแจ้งเจ้าของข้อมูลเมื่อเสี่ยงสูง |
| หลังปิดเหตุ | สรุปสาเหตุ · แก้ถาวร · เพิ่มชุดตรวจที่จับเหตุนี้ได้ · ทบทวน threat model |

## กักเหตุ (เลือกตามเหตุ)

- **บัญชีผู้ใช้ถูกยึด:** ลบแถวใน `tenant_users` ของผู้ใช้นั้น (ตัดสิทธิ์ทันที — บทบาทอ่านใหม่ทุกคำขอ) · Supabase → Auth → ผู้ใช้ → sign out / ban · ยกเลิกคำขอส่งออกที่ค้าง (`/app/exports`)
- **กุญแจรั่ว** (`PII_KEY` · `PII_HMAC_KEY` · `DATABASE_URL` · `ANTHROPIC_API_KEY`): หมุนกุญแจที่ต้นทาง → อัปเดต Vercel env → redeploy · `PII_KEY` รั่ว = ข้อมูลติดต่อทั้งฐานถือว่ารั่ว (การหมุนต้องเข้ารหัสใหม่ทั้งตาราง — งานแยก)
- **AI ทำงานผิด/รั่วผ่าน prompt:** ตั้ง `AI_DISABLED=1` ใน Vercel (ปิดทุกบัญชี) หรือปรับ `tenant_billing` ของบัญชีนั้น
- **ช่องโหว่ในโค้ด:** revert ผ่าน Vercel (Instant Rollback ไป deployment ก่อนหน้า) แล้วค่อยแก้

## เก็บหลักฐาน (ก่อนแก้)

- `audit_log` และ `activity_log` ช่วงเวลาที่เกี่ยวข้อง · ตรวจสายไม่แตกด้วย `verifyAuditChain`
- `export_requests` (ใครขอ/อนุมัติ/ดาวน์โหลดเมื่อไร กี่แถว) · `dsar_requests`
- Vercel runtime logs · Supabase auth logs
- ห้ามคัดลอกข้อมูลส่วนบุคคลลงเอกสารเหตุ — อ้างรหัสแทน
