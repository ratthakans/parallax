# Runbook · กู้คืนฐานข้อมูล

ใช้เมื่อ: ข้อมูลเสีย/ถูกลบผิด · migration พัง · ซ้อมกู้คืน (อย่างน้อยไตรมาสละครั้ง และก่อนรับข้อมูลจริง)
ผู้ทำ: เจ้าของระบบ (ต้องเข้า Supabase dashboard ได้) · บันทึกทุกขั้นในตารางท้ายเอกสาร

## ก่อนเริ่ม

- [ ] ระบุเวลาที่ต้องการย้อนไป และเหตุ · แจ้งผู้ใช้ว่าระบบจะหยุด
- [ ] **ส่งออกทะเบียนการลบจากฐานปัจจุบัน ทุกบัญชี** — backup ที่ทำก่อนการลบจะพาคนที่ลบแล้วกลับมา
  ```bash
  DATABASE_URL=<production> npm run erasures -- export <tenant> erasures-<tenant>.json
  ```
  ไฟล์มีแค่ HMAC/เหตุผล/เวลา แต่ยังเป็นข้อมูลส่วนบุคคล — เก็บในที่ปลอดภัย ลบเมื่อเสร็จ
- [ ] ปิดการเขียน: Vercel → ตั้ง `AI_DISABLED=1` และ redeploy หน้า maintenance (หรือ pause project ถ้าเสียหายหนัก)

## กู้คืน

1. Supabase → Database → Backups → เลือกจุดกู้คืน (แผน Free: รายวัน · Pro + PITR: ระดับวินาที)
2. Restore แล้วรอจนสถานะพร้อม — **จดเวลาเริ่ม/จบ** (ใช้วัด RTO)
3. ตรวจสคีมาตรงกับโค้ด:
   ```bash
   DATABASE_URL=<production> PARITY_REQUIRED=1 npm run verify:schema
   ```
   ไม่ตรง = backup เก่ากว่า migration ล่าสุด → รัน migration ที่ขาดตามลำดับใน `supabase/migrations/`
4. ใช้ทะเบียนการลบซ้ำ ทุกบัญชี:
   ```bash
   DATABASE_URL=<production> npm run erasures -- reapply <tenant> erasures-<tenant>.json
   ```
   ผลบอกจำนวนรายการที่ใส่กลับ และจำนวนคนที่ถูกลบซ้ำ — บันทึกไว้
5. ตรวจสายบันทึกตรวจสอบไม่แตกทุกบัญชี — `verifyAuditChain(tenant)` ใน `lib/engine/audit.ts` (ยังไม่มีหน้าจอ เรียกจากสคริปต์)
6. เปิดระบบ · ลองเข้าสู่ระบบ · เปิดหน้าวันนี้ · ค้นรายชื่อ
7. **วัดผล:** RPO = เวลาที่เกิดเหตุ − เวลาของ backup ที่ใช้ · RTO = เวลาเปิดระบบ − เวลาที่เริ่มหยุด

## เป้าหมาย (plan หัวข้อ 12)

RPO ≤ 1 ชม. · RTO ≤ 4 ชม. — **แผน Free ทำ RPO ได้ราว 24 ชม. เท่านั้น** (threat model G2) ต้องใช้ PITR ก่อนเสนอตัวเลขนี้ในสัญญา
